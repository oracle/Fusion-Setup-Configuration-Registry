## Lookup Execution Rules

For check_stocking_location_technician_assignment, invoke the declared shared REST client with GET, no body, and REST-Framework-Version: 9. Confirm the current principal can see all relevant technician assignments; a successful filtered GET alone does not establish unrestricted visibility. Follow pages until hasMore=false, advancing by the returned paging information and rejecting non-progressing pages. Keep parent/assignment IDs transient and persist only redacted outcomes/counts. Reuse the result only within the same validated preview context; after a changed target or resumed/stale preflight, refresh the read-only check before dispatch. An unavailable query/filter is a contract failure; do not guess another finder or interpret it as no assignment.

For child-only Site Dedication imports, use the child lookup contract verified in the earlier user-requested import workflow. Do not infer that a parent is absent from aggregate loader counts.

| Situation | What Happens |
|---|---|
| Live lookup | Use core/fusion-api/rest-api-client/scripts/fusion_rest_client.py with the selected environment and REST-Framework-Version: 9. Pass finder, q, fields, onlyData=true, limit, and offset as separate --query arguments |
| Special characters in user input | Safely escape confirmed Fusion string literals and encode through the client. If safe representation is uncertain, use the confirmed finder with pagination and exact in-memory comparison; never loosen the match |
| Empty, paginated, malformed, or rejected response | Count matches only after all pages. Do not substitute sample placeholders, cached IDs, or another environment. Report auth/authz, transport/environment, or Fusion API failures separately |
| ID supplied instead of name | Verify it through the same resolver and require any additional supplied name/code to agree. An ID does not permit skipping organization-scoped subinventory selection |
