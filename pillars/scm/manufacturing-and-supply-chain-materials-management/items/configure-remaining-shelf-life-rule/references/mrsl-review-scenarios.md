# MRSL Review Scenarios

These synthetic cases describe expected outcomes for offline SME and developer
review. They have not been executed against Fusion. They do not replace live
metadata validation, the selected Run Book, Data Loader preview and approval,
or the task's authoritative rules. Record actual execution evidence separately
through the owning workflow when that work is requested.

## Shared Review Context

- Use the synthetic rule name `SYN_MRSL_A`, rule ID `101`, existing catalog ID
  `201`, alternate catalog ID `202`, category ID `301`, and item ID `401` only as
  hypothetical lookup results. They are not known records in any environment.
- Existing header context has Description `Original`, DemandAnchorDateType `2`,
  and CategorySetId `201`. Keep that context separate from requested changes.
- For mutation cases, assume an exact registered `remainingShelfLifeRest`
  schema and a validated target. Generate the request-wide
  RemainingShelfLifeRuleId through the owning skill in the schema-required
  format; this document does not prescribe a literal value or generation format.
- Always include the populated `remainingShelfLifeRest` parent record. It is
  distinct from the `rule` component. Use only requested operation components,
  the required POST request controls, and the current task's approval contract.
- Treat lookup rows below as complete hypothetical results unless a case
  explicitly tests failure or pagination. Retain synthetic names as lookup
  context rather than adding undeclared loader columns.

## Assignment Scope Coverage

For each AssignmentType code `1` through `20`, use the exact matching Required
Groups row in [input validation](../ora-resource/ora_input_validation.md):

1. Review a new detail with MRSLDays `10` and every required input for that code.
   With successful applicable lookups, schema checks, and design gates, it may
   reach preview; readiness alone does not authorize submission.
2. Omit each required input in turn and expect a missing-input blocker naming
   that field and detail. Keep all other required inputs present.
3. For category-level codes `11` through `20`, repeat the missing-header-catalog
   case even when CategoryId is supplied directly.
4. For codes `7`, `8`, `17`, and `18`, use S10's alternative location branches
   rather than requiring both geography and zone.

Reviewers should record case IDs, observed results, evidence references, and
deviations during the next audit. These expected outcomes are specification
evidence, not an automated MRSL business-rule test suite.
