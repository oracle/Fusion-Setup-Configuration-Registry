# Configure Remaining Shelf Life Rule Design Enforcement

## Scope

Enforce the developer-supplied operation mapping and preservation of header attributes. The rule object is permitted only when the user requests creation of a new Remaining Shelf Life Rule or update of an existing Remaining Shelf Life Rule. An existing header may update any requested subset of Description, DemandAnchorDateType, and CategorySetId while preserving every unrequested header attribute. The owning runbook and core.data-loader workflow prepare the objects and retain payload, approval, and submission ownership. This gate validates their prepared selection and preservation evidence through the existing declared execution contract.

## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Establish validation readiness | Require the preceding input-validation and applicable lookup steps to pass. |
| 2 | Enforce header count, update preservation, and object selection | Allow at most one new Remaining Shelf Life Rule header in the complete task request and its prepared sources. Permit rule only for an explicitly requested header create or update. For each header update, enforce the requested-field scope and preservation evidence in the Design Rules below. For every requested detail operation, enforce its corresponding object. Required Data Loader request-field checks are owned by the preceding input-validation step. |
| 3 | Return enforcement result | Pass only when any prepared rule object has a matching header create/update intent, each header update preserves every unrequested attribute, and each requested detail uses its required object. Block unauthorized changes, missing preservation evidence, mismatched selections, or ambiguity before preview and submission. A header-only request has no detail-object requirement. |

| A header-only update is requested | Error | | The preparation includes an unrequested detailCreate, detailUpdate, or detailDelete operation. | Prepare only the registered rule update with its required parent and linkage/control fields. Never repair captured records in place or reuse approval after changing data or target context. | No; report the correction to the owning workflow. |
| User wants to add or create a new Remaining Shelf Life Rule Detail | Error | | The owning workflow has not prepared the new detail in detailCreate, or has selected detailUpdate or detailDelete for that operation. | Prepare the new detail in detailCreate through the owning workflow and revalidate. | No; report the correction to the owning workflow. |
| User wants to update an existing Remaining Shelf Life Rule Detail | Error | | The owning workflow has not prepared the existing detail change in detailUpdate, or has selected detailCreate or detailDelete for that operation. | Prepare the existing detail change in detailUpdate through its declared update workflow and revalidate. | No; report the correction to the owning workflow. |
| User wants to delete an existing Remaining Shelf Life Rule Detail | Error | | The owning workflow has not prepared the existing detail deletion in detailDelete, or has selected detailCreate or detailUpdate for that operation. | Prepare the existing detail deletion in detailDelete through its declared delete workflow and revalidate. | No; report the correction to the owning workflow. |
| The requested detail operation is missing, conflicting, or ambiguous | Error | | A unique operation-to-object mapping cannot be established for the affected detail. | Obtain an explicit add/create, update, or delete intent before the owning workflow prepares the detail object. | No |

## Sources

- Existing Data Loader source preparation serializes retained workbook headers and cells; a blank full-template cell is not proof that the corresponding outgoing attribute is omitted.
- Developer instruction: add/create new detail requires detailCreate; update existing detail requires detailUpdate; delete existing detail requires detailDelete.
- Developer instruction: rule must be prepared only if the user wants to create a new Remaining Shelf Life Rule or update an existing Remaining Shelf Life Rule.
- Developer instruction: the user cannot add more than one Remaining Shelf Life Rule; enforced as at most one new rule header per complete task request.
- The existing owning Data Loader workflow retains prepared-source validation, payload construction, preview, approval, and submission ownership.

- Developer reversion: Region uses addressGeographies/GeographyIdentifierId and Zone uses geoZones/ZoneId. Multiple name-matching records require explicit user selection; selection context includes returned hierarchy or zone metadata.
