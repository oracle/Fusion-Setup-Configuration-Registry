# Configure Remaining Shelf Life Rule Error Handling

## Sources and Boundary

Use the repository governance/error-handling-guidelines.md and the FusionApps Resource Authoring execution guide for classification, disclosure, and stop-before-retry behavior. Preserve the actual Fusion status and sanitized message rather than inventing product error-code mappings. Processing, preview, approval, and submission remain with the selected runbook and core.data-loader workflow.

## Error Situations

| Situation | What Should Happen |
|---|---|
| Skill-generated request linkage is missing or inconsistent | Block preview and submission under ora_input_validation.md. Identify the affected section/record and the missing generation context, missing value, schema-format failure, request-wide mismatch, or parent-linkage failure. Return it to the owning source-preparation workflow under ora_defaulting_rules.md; do not ask the user to supply RemainingShelfLifeRuleId or fill/replace captured values. Corrections after capture require corrected preparation, a fresh validation session, and fresh approval. |
| Required input or lookup cannot be validated | Stop with the affected field, failed check, and required correction. Eligible read-only query syntax/type errors may first use Controlled query recovery owned by ora_reference_lookups.md; other failures and exhausted or unsupported recovery stop. Use the owning input-validation or reference-lookup contract; do not substitute a value or mark a failed check passed. |
| Required input is missing or invalid | Report the field and the concrete requirement from ora_input_validation.md without submitting data. Revalidate corrected input through the owning workflow. |
| A header update would overwrite an unrequested attribute | Block preview and submission under ora_design_enforcement.md. Identify the affected attribute and whether the cause is a changed value, ambiguous blank/null serialization, or missing preservation evidence. Return the source for validated omission or verified unchanged-value preparation through the owning workflow; corrections to captured data require a fresh session and approval. |
| Zone no-match, requested-page failure or ambiguous selection | Only a valid empty initial page with hasMore=false returns INVALID ZONE. A valid hasMore=true page offers displayed-record selection or Next 25 and waits; unread pages are not failed evidence. Stop on a failed requested page, malformed/nonadvancing metadata, ignored filtering, unresolved choice, changed selected ZoneId/code/type/category identity or captured-ID conflict. Follow resolve_mrsl_zone; never silently pick a row, auto-select a sole later-page record, switch Region/Zone branches or edit captured values. |
| Customer requested-page failure or invalid navigation evidence | A valid hasMore=true page offers selection or Next 25; unread pages are not a failure and must not trigger automatic continuation. Stop on a failed requested page, invalid metadata, nonadvancing offset, missing selected identity or ambiguous option mapping. Report sanitized diagnostics without claiming uniqueness or absence. Follow the customer resolver for a fresh valid page/selection; never pick a different customer or edit captured data. |
| Reference filter rejected or ignored | Stop the affected lookup and report the declared field, finder scope and sanitized service diagnostic. Follow ora_reference_lookups.md for filter and completeness checks. Do not remove the filter, guess a bind, switch endpoints or scan unfiltered data; an HTTP 200 response containing unrelated values also fails validation. |
| Region requested-page failure or ambiguous hierarchy selection | A valid hasMore=true response offers the displayed choices or Next 25 and is not incomplete evidence merely because later pages are unread. Stop the invocation on failed requested pages, malformed/nonadvancing pagination, ignored filtering or a missing/changed selected hierarchy. Preserve full selected-record context through GeographyLevel5Value; never silently switch same-ID variants, auto-select a sole later-page row or modify captured data. |
| A task-specific Fusion business error is returned | Stop and classify as fusion_api_error. Preserve HTTP status, endpoint path, sanitized Fusion message, and diagnostic reference when available. Query syntax/type errors are distinct from business errors and may use only the bounded read-only recovery contract in ora_reference_lookups.md. Correct the reported cause before a fresh validation run; never guess a recovery action or replay a write. |
| A mutation has a partial or uncertain outcome | Stop and report confirmed results separately from the unknown outcome. Keep the existing request or job reference for reconciliation by the owning workflow when requested; do not create a replacement request or retry automatically. |

## Error Classifications

| Result Category | When Used | Next Action |
|---|---|---|
| input_validation | Required values or their authoritative validation contract are missing | Obtain the input or complete the contract before validation resumes. |
| catalog_or_metadata_mismatch | Selected task or BO identity cannot be resolved unambiguously | Stop and correct the mapping through its owning workflow. |
| auth_expired_or_invalid | A cached token is rejected | Delegate authentication handling to core.auth.fusion-oauth-authentication; never replay a write automatically. |
| transport_or_environment | Communication fails or a submission outcome is unknown | Stop and distinguish a read failure from an uncertain mutation. |
| fusion_api_error | Fusion returns a task-specific error | Report the sanitized server diagnostic and failed stage. Correct the cause or investigate through the owning workflow before a new validation attempt; do not replay a write. |

## Disclosure Rules

| Gate | What Must Be Shown |
|---|---|
| Validation or enforcement blocker | Selected task, failed stage, missing contract or input, and one corrective action. |
| Partial or uncertain outcome | Confirmed results, uncertainty, and a safe next action; redact credentials, tokens, payload copies, and sensitive customer data. |
| Task-specific Fusion error | Selected task, environment, failed stage, HTTP status when available, sanitized server message, confirmed outcome or uncertainty, and one supported corrective action. Never expose credentials, tokens, authorization codes, payload copies, or sensitive customer data. |

## Refusal Rules

| Situation | What Must Not Happen |
|---|---|
| A required check, lookup, or owning execution contract is missing or invalid | Do not claim readiness, invent a lookup or payload, or submit data. Report the affected contract and return the issue to its owner. |
| A write failed or its outcome is uncertain | Do not retry a task mutation or Data Loader submission automatically. |
| Task inputs or target change after preview | Do not reuse the earlier approval; follow the owning Data Loader validation and approval workflow again. |

## Sources

- Developer instruction: RemainingShelfLifeRuleId is mandatory and automatically generated by the owning skill exactly once per complete request using the existing Data Loader schema required format, constant across all sheets and populated parent/child records for every supported operation, and propagated before capture. Do not request the value from the user. It remains distinct from Fusion-generated MRSLRuleId and MRSLRuleDetailId. Missing generation context or missing/invalid/different values blocks preview and submission; captured-source corrections require fresh preparation, validation and approval.
- Developer instruction: header updates must not overwrite other attributes; allow a description-only update while preserving demand anchor date type and catalog.
- Developer request: remove error-handling placeholders while preserving the existing task workflow.
- Repository governance/error-handling-guidelines.md: failure classification, sanitized diagnostics, partial outcomes, and retry boundaries.
- FusionApps Resource Authoring task-node execution guide: validation evidence, terminal results, and preview/approval boundaries.
- Existing owning core.data-loader workflow: source validation, immutable preview approval, single-attempt writes, and requested status/reconciliation handling.
