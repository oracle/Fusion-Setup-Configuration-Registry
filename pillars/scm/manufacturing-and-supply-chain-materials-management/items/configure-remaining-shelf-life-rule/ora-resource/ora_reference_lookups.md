## Lookup Execution Rules

The MRSL header resolver uses the CategorySetId returned by SpEgpCatalogLookupV1 for
rule.CategorySetId after matching the supplied name to CategorySetName. Category-level details use that header value
as the finder bind bCategorySetId for SpEgpCatalogCategoriesV1. Neither itemCatalogs nor categorySets
is a replacement or fallback for the declared header finder.
Existing headers are read-only context; this correction does not authorize
automatic repair of previously stored IDs or require a catalog on every header.


| Situation | What Happens |
|---|---|
| Existing header and detail retrieval order | Use resolve_mrsl_rule_header to resolve a supplied MRSLRuleName before list_mrsl_rule_details consumes its MRSLRuleId. Retrieve existing context before input checks that require target identity, header preservation evidence, or existing detail scope. For new-header creation without an existing-information request, both retrievals return not_applicable; absence of an existing header does not block creation. Header-only requests do not require a detail read. Explicit read requests remain read-only and return their retrieved context without preparing or submitting a mutation. |
| Zone lookup applicability | Use resolve_mrsl_zone for ZoneName, Zone, or GeographyName explicitly supplied in the Zone branch. No Zone branch returns not_applicable; unclear Region/Zone context requires clarification. Preserve the location alternatives for types 7, 8, 17 and 18. |
| Zone preparation and captured-source validation | Before capture, resolve through filtered geoZones pages using one requested page at a time. Use a valid explicit displayed-record choice, or auto-resolve only a sole initial-page record with hasMore=false. Retain name/environment, q, page offset and count, stable option mapping and ZoneId/code/type/category identity. Unread pages do not prevent explicit selection. During Task Hook validation re-fetch the selected page with the same filter, projection and offset; require the identical selected record to remain present and its ZoneId to agree with captured data. Do not read all pages or ask again while the retained explicit choice is valid. Missing/changed identity, failed requested-page evidence or captured-ID conflict requires clarification or fresh preparation/validation; never silently select another record or edit captured values. For an originally auto-resolved result, revalidate the sole initial-page record and hasMore=false; new ambiguity requires selection. |
| Region assignment location routing | For effective AssignmentType 7, 8, 17, or 18 only, consume the Region assignment location alternatives validation from ora_input_validation.md. When geography details are supplied, run resolve_mrsl_geography to derive geography_id (region_id). When zone details are supplied, run resolve_mrsl_zone to derive zone_id. The absent alternative returns not_applicable without a request and is not a missing-location failure. If both branches are supplied, validate both, retain their separate outputs, and require the owning workflow to validate their existing registered field mappings; never cross-populate a geography ID as a zone ID or a zone ID as a geography ID. Missing, ambiguous, invalid, or conflicting supplied details block under the applicable resolver. This routing rule does not add required location input to any other assignment level. |
