## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| New header with nested new children | Contract metadata may be reused for the same confirmed deployment/context; no existing-record, duplicate or usage lookup is required |
| Conditional child navigation | Resolve header first, primary resource next, alternate last. New children beneath a newly prepared parent use the parent relationship; do not query IDs that do not exist yet |
| Data Loader names versus REST navigation | A DAT section discriminator is not a REST child URL or finder. Confirm the actual child definition through read_standard_operation_contract and follow returned links; do not replace a REST child name with StdOpAlternateResource solely because that is the loader section name |
| Selecting target links | Use same-environment service-returned self/child links and validated hierarchy. Do not manufacture hash keys, follow arbitrary user URLs, or forward authorization to another origin |
| Query safety | Escape and URL-encode filter values. Retain links needed for navigation; do not request onlyData=true or suppress required child links. Do not mix fields and expand or filter on non-queryable attributes |
| Current values | Retrieve every field needed for intended-change comparison. A missing response field differs from an explicit null; do not assume equality or absence from missing data |
| Reference selection on create | Use supported IDs or documented code inputs. Server code-to-ID resolution owns organization, work center, resource, supplier/site and maintenance-code validation; do not duplicate those lookups just to predict a write |
| Code versus ID | Prefer one representation per reference. For update use writable IDs where code fields are read-only; do not send conflicting pairs or assume the winning value matches intent |
| Supplier item eligibility | Rely on server validation for OSP item eligibility; do not add a separate eligibility resolver or disclosure gate |
| Tenant metadata | Use read_standard_operation_contract for exposed DFF/attachment definitions and metadata links. StandardOperationDFF and StandardOperationResourceDFF loader headers identify flexfield families, but their context/display columns do not establish tenant segments, valid context values or REST writability. Absence of an attachment section from a DAT template does not establish absence of REST attachment support. If required context, segments, category or upload requirements are not exposed or supplied through a declared core capability, stop only that requested extension; do not invent a lookup or route |
| Runtime contract | Reads require the selected core client, environment identity and authorization. Use its confirmed REST framework version and metadata context. Reuse matching evidence only while valid; refresh after changes |
| Avoid duplicate validation | Do not query duplicates, work-center capacity, reference usage, active dates or simultaneous-resource graphs merely to reproduce server checks. Reconciliation after an uncertain write is a distinct authorized purpose |

Runtime metadata and selected-record values are authoritative Fusion evidence. Supplied task values establish intent only. No private database, UI helper or internal service path is a lookup route.
