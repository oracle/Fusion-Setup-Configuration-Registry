## Equipment Identity Procedure and Route Limits

The equipment request and field definitions apply to both selected Workstations routes. FSM CSV values remain subject to `verify_workstations_csv_contract`; a REST workbook remains subject to its current generated attribute/key definitions and registered METADATA preflight. Neither route may skip equipment eligibility. Apply FSM template, CSV-format, task CSV-support and package checks only to an explicitly selected FSM task CSV package. For an explicitly selected REST Data Loader workbook, those FSM-only checks are not applicable. Continue the applicable common field, organization, Work Center, equipment and location checks using the supplied validated inputs and the current generated REST attribute/key definitions. Missing or ambiguous input-route context remains unresolved; do not infer REST from missing FSM findings. This clarification uses the existing Applies When conditions and outcomes; it adds no REST execution branch and establishes no runtime result.

1. Require the selected workflow's successful organization and Work Center identity results. Use the original lossless decimal ID representation, never a rounded number. Before any request, confirm the same target's current describe exposes every requested resource/child/LOV field and the documented child link.
2. Read every productionResources page for the verified organization. Verify each returned OrganizationId and preserve its ResourceType. Resolve the supplied equipment identity across the complete scan and require its parent ResourceType exactly EQUIPMENT, the supported code in the complete Manufacturing Resource Instances contract; LABOR, missing, null or unknown types cannot satisfy this association. Do not infer a numeric type or silently discard conflicting identities. Follow only the actual EquipmentInstance child collection link from that same resource/target; do not construct a child key from a display name or follow a foreign-host link. Escape apostrophes in the q value by doubling them, and let core.fusion-api.rest-api-client encode parameters.
3. Read every child page. Across all parent resources, require exactly one exact EquipmentIdentifier equal to the supplied EquipmentInstanceCode, with positive lossless EquipmentInstanceId, OrganizationId and ResourceId. Its OrganizationId must equal the verified organization and its ResourceId must equal that parent. Reject nonexact returned rows and conflicting/multiple identity results rather than silently filtering them into a pass. Preserve both parent and child InactiveDate values; null and non-null dates have different source implications and must not be replaced with the laptop date.
4. Read all workstationEquipmentInstancesLOV pages for that EquipmentInstanceId, including association rows outside the intended Work Center. Every returned equipment code, organization and resource must agree with the resolved identity. Record WorkCenterId and WorkstationId without treating one primary Work Center field or zero LOV rows as complete membership/association proof. This LOV has no equipment/resource inactivity predicate; a returned row does not prove active equipment.
5. For the resolved parent ResourceId and verified WorkCenterId, GET /fscmRestApi/resources/11.13.18.05/workCenters/{WorkCenterId}/child/WorkCenterResource with q=ResourceId={ResourceId}, fields=WorkCenterId,ResourceId, onlyData=true, limit=100 and offset=0 through the same selected shared client. Confirm same-target describe compatibility before executing and complete every page under the paging rules above. Require at least one exact row with both IDs equal to the resolved inputs; reject conflicting or malformed rows. The EO tests membership with hasNext, so do not invent a requirement that exactly one row exist or substitute PrimaryWorkCenterId for this membership check. Zero rows after complete authorized coverage fail membership; read/permission/paging failure means unable to validate.
6. Return the identity fields, both raw inactive dates, exact resource type, complete membership finding and raw association findings to the selected validator. Keep authoring completeness separate from eligibility: return the actual verified, failed or unverified date/assignment findings; no local finding bypasses authoritative service validation. A no-match result after complete authorized coverage blocks the supplied reference; an authorization/service/paging failure means unable to validate. Neither result permits positional selection, a waiver, a new equipment record, a load or a retry of a prior import.
