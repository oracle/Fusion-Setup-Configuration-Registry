# Design Enforcement

## Server-managed create reconciliation

These are task policies for the supported create-and-verify path. They do not
claim that schema validation proves the resulting Fusion state. Lookup mechanics
and source evidence belong to ora_reference_lookups.md.

| Contract ID | Applies When | Required Evidence and Decision | If Not Satisfied |
|---|---|---|---|
| WC.RECON.SHIFTS | A new work center requests generated plant-default resource shifts | Require a new parent and new resource associations, plant-default routing, explicit Available24HoursFlag=false, unique complete resource/shift identities, no named schedule or override-calendar source, and every requested shift's units equal to its resource's ResourceQuantity. The fresh product describe must confirm automatic shift creation. Preserve the complete requested shift set as expectations; omit only the generated shift write rows. | Block this route for existing resources, unequal units, missing generation evidence, duplicate identities, named schedules, or override calendars. A different supported assignment route needs its own validation and approval. |
| WC.RECON.TYPE | A create requests a nonblank WorkCenterSubInvType that is not writable | Require the exact loader template to recognize the field and its workCenters parent mapping, plus fresh same-target product describe evidence of updatable=false, allowChanges=never, and a nonblank defaultValue exactly equal to the requested value. SubinventoryName and LocatorId must be writable. Omit only this field from the write source and preserve its exact value as an expectation. A retained write field still requires writable loader evidence. | Missing or ambiguous metadata, another operation, a different default, or an unwritable sibling field blocks as catalog_or_metadata_mismatch. No local default, inferred writable flag, waiver reuse, or silent value replacement. |
| WC.RECON.BINDING | Preparing a create-and-verify preview | Bind the exact source SHA-256, target environment fingerprint, resolved parent/resource/locator identities, and complete original requested values to an immutable expectation artifact and its digest. Approval covers both source and expectation digests. | Any source, target, or expectation change invalidates validation and approval. Do not reconstruct expectations from the observed post-load state. |
| WC.RECON.READBACK | The bound Data Loader request succeeded | Require fresh complete declared GET evidence: all requested work-center values; each exact resource and quantity; persisted Available24HoursFlag=false; plant-default routing with zero effective overrides and resolved ManufacturingCalendarId; the complete one-to-one shift set with exact names, unique numeric IDs, correct PlantCalendarId and units; and exact subinventory type and locator. Check every requested component before reporting completion or all-load-success. | Missing, extra, duplicate, wrong-calendar, wrong-unit, wrong-type or wrong-locator results, incomplete paging, a failed GET, or a binding mismatch leaves reconciliation incomplete. A successful loader request alone is not completion. |
| WC.RECON.RESUME | A successful load has pending or failed reconciliation | Preserve its request ID and accepted source and expectation digests. Resume only the declared GET verification against those unchanged expectations. | Never replay the accepted create. Corrections require a separately supported, validated and approved source. Unknown load status must first use core.data-loader monitoring; it is not permission to resubmit. |

## Calendar and resource policies

Apply these policies to the normalized request regardless of how it was supplied.
The target environment is the Fusion environment selected by the active workflow.
Direct requests use their supplied business intent and the declared target lookups;
an FSM export is not required. Each row's Applies When condition controls its scope.

| Contract ID | Applies When | Required Evidence and Decision | If Not Satisfied |
|---|---|---|---|
| WC.CALENDAR.PLANT_IMMUTABLE | Any explicit production-calendar create, update, end-date, or delete request, including a natural-language prompt or structured input | Resolve the parent's target plant ManufacturingCalendarId before preparation. Resolve a supplied Name or ScheduleName to its ScheduleId in the target environment; for an existing ProductionCalendarId, use the parent-scoped persisted association's MfgCalendarId. Verify any supplied identifiers agree. Reject the requested mutation when the selected calendar ID equals the plant ManufacturingCalendarId: this association is application-managed. This protection applies even when the caller supplies only numeric IDs. | Do not turn an explicit protected-calendar mutation into a successful no-op, send it to Data Loader, or use another write route. Explain the rejected target and retain other independent eligible changes under the normal batch policy. |
| WC.CALENDAR.EXISTING_OVERRIDE_PATCH | An update or end-date request targets an existing nonplant production-calendar association | Match the requested association to exactly one target association by parent, target-resolved MfgCalendarId and ProductionCalendarId, then compare its persisted start and end bounds. If AssociationStartDate is unchanged, omit it from the PATCH; omit the whole association data row when no supported field changes. Include a changed start date only for an explicit start-date-change intent and retain it for Fusion's future-date validation under WC.CALENDAR.SERVER_DATES. Do not turn an existing association into a POST or rewrite its current start merely because the input includes it. | Missing or ambiguous association identity, an unsupported changed field, or an unreviewed start-date change blocks source preparation. A server WIS-4440558 rejection requires a new reviewed source and approval; do not retry the same ZIP. |
| WC.CALENDAR.MIXED_SCOPE | One normalized request contains calendar changes and resource additions on existing Work Centers, from direct input or FSM exports | Partition stage selection by OrganizationCode and WorkCenterCode and by work_center, calendar_association or calendar_resource scope. Validate every independent parent and retain each parent's errors. Keep the complete original request and pending outcomes bound to every source; for FSM input, retain the entire original task delta. Compatible ready stages with distinct parents and the same operation scope may share one immutable Data Loader source and approval, including existing-parent resource_create stages that satisfy WC.CALENDAR.RESOURCE_CREATE_BATCH; explicitly list included, excluded, and deferred parents. Establish each parent's calendar prerequisite before its override resource create; then establish new resource associations before explicit assignment work. A separate plant-default parent keeps its own false override route. Verify all members of an accepted batch before advancing their dependent stages. | Do not include an invalid or dependent parent in the approved source, select the calendar branch for every parent because one parent changes its calendar, discard requested resource changes, or complete the whole task after only one parent or stage matches. A batch failure or partial load requires status and row-level reconciliation before any new source; never assume the whole batch succeeded or retry it automatically. |
| WC.CALENDAR.RESOURCE_CREATE | An existing Work Center receives a new resource association from direct input or an FSM export | Use New work-center resource identity and New resource source mapping from ora_input_validation.md. Resolve a supplied ResourceName or ResourceCode through resolve_active_production_resource in the parent organization and verify every supplied identity. A numeric ResourceId-only request uses core.data-loader validation and does not require an export. For FSM ResourceCode input, optional same-run name enrichment through enrich_exported_resource_name must agree with the target resolver; the live organization-scoped code lookup does not require a master export. Resolve the parent and its persisted calendar route. For an override create derive WcProdCalendarId from that parent's sole effective ProductionCalendarId. Require the exact live child template, positive target ResourceId and WorkCenterId, retained quantity and flags, and explicit POST with no generated WorkCenterResourceUniqID. After a bound successful load, verify the same-target parent route, resource identities, quantities, flags and any requested generated shifts through verify_existing_parent_resource_stage. A returned null or blank WcProdCalendarId is valid nullable state; it does not require a calendar-specific lookup or hold completion or later override creates by itself. Use metadata-only ancestor sections; the parent is not created again. | Missing identity evidence, ambiguous identity, route mismatch, unsupported columns or an existing conflicting association blocks. Master-export name evidence is optional for FSM ResourceCode enrichment; target ResourceCode resolution is sufficient without it. A nonblank returned WcProdCalendarId that differs from the selected ProductionCalendarId remains a readback discrepancy; retain expected and observed IDs and hold the affected completion and further same-target override creates pending declared no-write reconciliation. A missing response field is distinct from an explicitly null or blank field and requires complete readback evidence. Plant-default resources may legitimately return a blank WcProdCalendarId. Existing resource updates and removals need a separate reviewed PATCH/DELETE mapping. A matching persisted association is verified without another POST; never replay an accepted create to repair readback. |
| WC.CALENDAR.RESOURCE_CREATE_BATCH | Preparing a new resource_create stage for existing Work Centers, including several resources under one parent or compatible independent parents | Retain batch creation. Include every compatible ready association selected for the artifact, preserving its distinct parent/resource identity, requested values, and immutable per-resource expectations. Validate every requested association and list included, invalid and deferred outcomes without discarding the complete original intent. Apply the Existing-parent resource-create artifact contract in ora_input_validation.md to the final archived bytes. Complete the ordinary exact parent/resource/shift readback for every accepted member before advancing dependent stages or claiming completion. Freshly matched existing associations are verified without another POST. | Stop on a source/expectation mismatch or missing, ambiguous or conflicting evidence. Preserve accepted sources and their unchanged declared readback and failed-resource inspection. Do not impose a one-row limit from aggregate failures, treat the absence of a generated create surrogate as evidence against batching, or invent WorkCenterResourceUniqID or SourceRef values to repair a loader identity rejection. A source check does not prove how the server transformed the rows; retain that distinction when diagnosing a load. |
| WC.CALENDAR.RESOURCE_IDENTITY_REJECTION | A resource_create load of any batch size fails with ResourceId/Name rejection and exact bound failed-resource inspection confirms requested associations are absent | Keep the failed request and per-resource identity evidence. Block automatic retry and corrective preparation of the same unchanged associations until reviewed loader or server evidence establishes a specific correction. Neither changing batch size nor repeating the same values identifies a correction. Any supported correction still requires fresh validation, an immutable source and normal approval. | Retain the adapter-generated downstream request/response or loader trace as the next diagnostic action; do not offer an unchanged replay. Conflicting or incomplete readback remains blocked under WC.CALENDAR.FAILED_RESOURCE_INSPECTION. Verified matching associations retain the failed job status and are omitted from subsequent creates; they need not block unrelated remaining work once ordinary inspection and stage gates pass. |
| WC.CALENDAR.GENERATED_PLANT_SHIFTS | A new resource association on an existing plant-default Work Center requests default shifts | Require persisted OverrideScheduleFlag=false, no effective override, resolved plant ManufacturingCalendarId, explicit Available24HoursFlag=false, no existing shift mutation/removal, unique complete requested shift names, units equal to the new ResourceQuantity, and fresh target describe evidence confirming automatic shift creation on production-resource assignment. Retain the full requested set as immutable expectations, omit generated shift writes, and require complete post-load readback of exact names, unique IDs, PlantCalendarId and units. | Unequal units, existing shift changes, named schedules or missing generation evidence require a separately supported assignment route. Missing, extra, duplicate, wrong-calendar or wrong-unit generated rows leave the stage incomplete and resume only bound GET verification. Do not widen WC.RECON.SHIFTS to existing-parent creates; this is a distinct calendar_resource create-and-verify contract. |
| WC.CALENDAR.STAGES | A normalized request requires a calendar change followed by resource or assignment work, from direct input or FSM exports | Bind each stage artifact, complete original intent, target, accepted request and stage result. Require successful core load and exact fresh declared readback before advancing. A final shift stage contains exactly one operation-specific child row; an availability conversion is a separate stage with authoritative numeric identity. | Keep task incomplete. Failed readback resumes unchanged GET verification; corrections require a new validated and approved artifact. |
| WC.CALENDAR.FAILED_INSPECTION | Core monitoring confirms a failed accepted calendar-association request | Retain the failed request, counts, error logs, approval checksum, immutable archive/preview/expectation digests and original target. Only declared GETs may compare the exact accepted calendar expectations to the target environment. A previously reviewed guidance snapshot may be used solely to inspect that accepted source. Report requested_calendar_state_verified separately when all calendar values match; report remaining explicit assignment work separately. | Binding changes, incomplete GETs or mismatches leave inspection incomplete. Never mark the failed job successful, complete the task, replay the archive, overwrite its preview, or prepare corrections without a fresh supported validation and approval. |

| WC.CALENDAR.FAILED_RESOURCE_INSPECTION | A bound resource-create batch has a terminal failed or partial core load result | Preserve the failed request, actual counts and resolved diagnostics. Require immutable archive, preview, expected resource identities and an exact retained copy of the preflight before inspect_failed_work_center_resources. Record every resource outcome while keeping the job failed. Corrective preparation requires complete inspection without conflicts or failed reads, fresh target checks, satisfaction of WC.CALENDAR.RESOURCE_IDENTITY_REJECTION when applicable, and a new validated artifact and approval; omit verified associations from any new POST. | Missing or changed evidence blocks inspection or recovery; never reconstruct an approval or missing preflight. No automatic retry, source rewrite, synthetic success, or whole-batch replay. Historical missing preflight evidence requires recovery of its exact original bytes or escalation. |

## FSM export input safeguards

Apply this table only when the supplied setup-data artifacts are FSM exports or
FSM export deltas. The source environment is the export origin. Normalize those
artifacts through FSM export normalization in ora_input_validation.md before
applying the general policies above. Direct requests skip this table and its
export-baseline and resource-master-export requirements.

| Contract ID | Applies When | Required Evidence and Decision | If Not Satisfied |
|---|---|---|---|
| WC.CALENDAR.EXPORT | An FSM delta changes the override flag, calendar intervals, or explicit override shifts | Normalize exports under ora_input_validation.md, resolve schedule and plant IDs in the target environment, exclude plant observations under WC.CALENDAR.PLANT_HISTORY, and compare the complete nonplant association state to its exported baseline. Retain unrelated changed child groups for their separately supported stage; reject unmapped fields before source preparation. Fusion validates interval business constraints during the approved load. Pair a false-to-true flag update with the required dated nonplant writes in chronological order, retaining their requested values as expectations and plant exclusions as audit evidence. | Recompare stale nonplant state or correct the exact source. Do not require changed translation rows for a calendar-only update. |
| WC.CALENDAR.PLANT_HISTORY | An FSM calendar delta contains a plant-calendar row, including first override activation or later synchronization | Resolve the target plant ManufacturingCalendarId through resolve_plant_manufacturing_calendar and each exported ScheduleName to its target ScheduleId. Exclude any row whose resolved ScheduleId equals that ManufacturingCalendarId from all productionCalendars POST, PATCH, DELETE, or MERGE data. Retain the original export and the resolved identity with an explicit exclusion reason for audit; its exported start/end dates are not upload, source-freshness, or completion requirements. Do not synthesize a predecessor end-date change. First activation still pairs the override flag update with at least one dated nonplant association write. Compare and verify the complete requested nonplant association set; verify the plant identity without asserting its exported dates. | Missing or ambiguous plant/schedule identity or a plant-calendar data row in the candidate source blocks preparation. A plant-only interval difference does not block other eligible rows or create an upload. Never filter an unrelated override or claim an excluded plant-calendar change was applied. |
| WC.CALENDAR.ROUTE_CHANGE | An FSM delta switches from plant default to override and the source export contains no old default-shift rows | Preserve the old rows as route-change evidence; do not infer deletion or an empty override assignment set. FSM resource-shift units cover the manufacturing plant calendar only. Fusion defaults resource and shift units for the new override calendar; absent FSM rows supply no override-unit mutation intent. Keep generated assignments untouched unless a separate explicit assignment request selects the documented route. | Stop when removal of named override assignments is requested without explicit DELETE intent; never synthesize DELETE or require zero generated assignments from source absence. |

## Calendar date validation authority

Fusion owns calendar business-date eligibility. During the approved REST load,
the server validates today/future restrictions, start-date changes, latest-calendar
deletion, schedule effectivity and interval ordering, overlap and continuity.
Local task validation checks required values, valid date serialization, identities,
explicit operation intent, source mapping and immutable approval bindings.
A prepared preview does not prove that Fusion has accepted the dates. Do not
invent a separate validation endpoint or execute a trial mutation before approval.

| Contract ID | Applies When | Required Evidence and Decision | If Not Satisfied |
|---|---|---|---|
| WC.CALENDAR.SERVER_DATES | Preparing or completing a production-calendar association mutation | Delegate business-date eligibility to Fusion's REST validation through core.data-loader. No local current-business-date input or mutation-date evaluator is required. Preserve requested ISO dates and historical expectations. Completion requires successful bound load status and exact fresh post-load readback. | A server date rejection is a failed load or Fusion API result, not local validation success or task completion. Preserve request and row errors, obtain a user-reviewed correction, and require a new validated immutable source and approval; never silently change dates or replay an accepted archive. |

## Source Boundary

This file owns business-policy gates only. The complete source evidence and REST lookup contracts are retained in ora_reference_lookups.md under Source Evidence. Core Data Loader owns source validation, approval, upload, and execution; this task never derives a REST item identity or performs a direct REST write.

## Enforcement Order

| Sequence | Step | What Must Happen |
|---|---|---|
| 1 | Work-center policy | For creation, confirm unique work-center values, resolve the active work area from OrganizationCode and WorkAreaCode, and retain its ID and name with the code in the source. For an update changing the work area, verify the selected area through the declared resolver. Do not run the active-work-area gate or request area fields for an update that leaves the area unchanged. |
| 2 | Calendar-association policy | Confirm complete target association state and source identities, apply WC.CALENDAR.PLANT_IMMUTABLE to explicit protected mutations, and apply WC.CALENDAR.EXISTING_OVERRIDE_PATCH to existing override updates. Apply WC.CALENDAR.PLANT_HISTORY only for FSM export input. Pair the first override indicator update with its new association when required, and apply WC.CALENDAR.SERVER_DATES without claiming server date acceptance at preview. |
| 3 | Calendar-route policy | Use the one route returned by the flag-and-effective-association lookup result. |
| 4 | Resource identity policy | Require numeric ResourceId in the final source for a new WorkCenterResource association; a business name or code is supported only after successful resolve_active_production_resource enrichment and source-mapping validation. For existing associations and resourceShifts operations, resolve supplied names when needed and confirm persisted resource and route-specific shift state; apply the shift-availability gate before final create/update approval. |
| 5 | Staged assignment-completion policy | Report prerequisite calendar-association and availability-conversion stages as intermediate; a separately validated final assignment source or the eligible WC.RECON.SHIFTS create-and-verify path can fulfill the requested outcome, each subject to its own completion checks. |
| 6 | Centralized Data Loader policy | Submit only the immutable artifact validated by core.data-loader after approval. |
