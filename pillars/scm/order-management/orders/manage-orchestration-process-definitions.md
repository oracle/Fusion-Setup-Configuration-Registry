# Manage Orchestration Process Definitions

- **Task code:** `DOO_MANAGE_ORCHESTRATION_PROCESS_DEFINITIONS`
- **Purpose:** Review and maintain definitions that specify orchestration processing, including fulfillment steps, rules, status conditions, release, and deployment, and verify assignment and business behavior with controlled orders.
- **Execution rule:** The user completes the approved change manually in Oracle Fusion **Setup and Maintenance**, on **Manage Orchestration Process Definitions** and the applicable assignment page, and performs manual validation in the tenant's **Order Management** user interface, with no API, import, automated configuration, or browser automation.

Use the [standard shared manual workflow](../../../../shared/common/manual-tasks/SKILL.md).

Provide manual steps directly from this task using the user’s supplied values. Stay within the documented guidance, identify missing details, and do not create separate guides or project artifacts solely to explain the steps.

## Manual steps

1. Confirm the approved change reference, environment and tenant release, functional and deployment owners, source process/version/status, target process/version, business units and set, process class, status rule set, changed steps and rules, assignment criteria, integration dependencies, and rollback owner. Start in nonproduction and confirm setup, deployment, and test-order access. Verify applicability of the supplied procedure to the tenant release and available controls. Resolve missing design details before editing. Specialized drop-ship, back-to-back, return, subscription, or other flows need their own approved process and integration requirements.
2. Select the approved path: review only, duplicate and adapt, create new, or maintain an existing custom process through supported editable-version controls. Use a suitable predefined process first; otherwise modify a copy, creating a new definition only if copying is insufficient. Do not edit the predefined original. Inventory required tasks, services, statuses, routes, business rules, and business-unit access. Define fulfillment outcomes, exceptions, branches, waits, pauses, revisions, cancellation, holds, recovery, checkpoints, and observation windows with their owners.
3. Open **Setup and Maintenance** and search for **Manage Orchestration Process Definitions**; task-search navigation varies by tenant. Locate the exact source process and version and capture the header, steps and sequence, status conditions, relevant rules, release/deployment evidence, and assignment setup. Preserve the prior working configuration and identify orders already using it. If the page or action is unavailable, verify access, selected version, and record state with the setup owner. For review-only work, record findings and proceed to applicable manual validation without changing setup.
4. For duplication, validate the source and resolve its errors before copying. Select the source and **Actions > Duplicate**, identify the new definition, and confirm you are editing the copy. Open **Status Conditions > Fulfillment Line Status Values > Edit Status Rule Set**, give the copied rule set an appropriate unique **Name**, then select **Save and Close** to avoid migration conflicts. Compare the copy with the source and identify inherited rules to preserve.
5. For an approved new definition, select **Actions > Create** and enter the header. **Process Name** automatically receives the required `CustomDOO_` prefix and has a maximum of 80 characters including that prefix. Use the approved **Process Display Name** without spaces, select a **Process Class** containing the required statuses, select the **Set** appropriate to the intended business-unit access, then select **Save**. For an existing released custom definition, use the tenant-supported revision procedure and record the actual action and source/target versions; the supplied procedure establishes no universal revision-button label.
6. On **Step Definition**, select **Actions > Add Row**, populate the approved **Step Name**, **Step Type**, **Task Type**, **Task**, and **Service**, then **Save**. Select the most recently added step before adding the next to preserve sequence. The supplied simple schedule-and-ship example uses **Schedule / Schedule / Create Scheduling**, **Reservation / Reserve / Create Inventory Reservation**, **Shipment / Ship / Create Shipping**, **Shipment / Ship / Wait for Shipment**, **Invoice / Invoice / Create Billing Lines**, and **Invoice / Invoice / Wait for Billing**, with **Shipped** as the shipping wait's **Exit Criteria**. Use these only where they match the approved flow; do not replace another flow with this example. Confirm missing task or service selections with the setup owner rather than substituting similarly named entries.
7. Review the applicable **Service**, **Conditional**, and **Merge** steps, branching and rejoin points, line-selection scope, planned dates/durations, wait and pause exit criteria, compensation, and integration destinations, operations, correlation, and error handling against the approved design. Record each planned request, response, and expected progression. Do not place scheduling, reservation, or shipping after billing. Before deleting a step, remove dependent process or line-status references that would prevent release. Confirm wait exits against task-status setup and resolve applicable rule gaps with the responsible owners before release; saving alone does not validate rule logic.
8. Confirm the intended **Process Class** and **Save**. In **Process Details > Status Conditions**, under **Orchestration Process Status Values**, select **Actions > Add Row**, set **Sequence** and **Status Value**, then use the **Expression** builder to select the intended task and status. Confirm the expression and **Save**. Ground expressions in the actual target task names and remove dangling references. Have the process owner review overlaps: conditions are evaluated sequentially, and the true condition with the highest sequence determines process status. Preserve required final process and line conditions for predefined shipment and invoice tasks.
9. For the approved custom target, open **Actions > Edit**, then **Actions > Release**. Review validation, resolve blocking errors, and assess and record warnings before retrying release. Confirm **Released** status; release makes the definition read-only and generates deployment artifacts. If it remains **New**, inspect validation and source-copy history; a faulty source may require correction before recreating its copy. For missing-task errors, compare removed steps with status and rule references.
10. Select **Actions > Deploy Process**, enter any prompted password directly in Fusion without recording it, and select **Deploy**. Retain the exact target/version, messages, and confirmed deployment outcome. If deployment is uncertain or failed, involve the deployment owner before repeating it or submitting test orders. Releasing another version on the same day requires rejecting the earlier version first; coordinate that specific action with the deployment owner rather than treating it as a general rollback. The predefined `ShipOrderGenericProcess` and `ReturnOrderGenericProcess` require deployment without release.
11. With the assignment owner, open the setup task **Manage Process Assignment Rules for Sales Orders**, whose page is **Manage Orchestration Process Assignment Rules**. Inspect the intended rule and confirm its action selects the target **Process Name (Order Fulfill Line)**. Use exact case when searching; undeployed processes are not found by that search. Only if an assignment change is approved, capture its baseline, save through supported controls, then activate and publish the rule. Define matching and nonmatching test orders. Deployment alone does not establish assignment.
12. In the tenant's **Order Management** work area, create a new controlled order meeting the assignment criteria and submit once. Capture order, revision, and fulfillment-line identifiers. Open available fulfillment and orchestration details and record actual navigation. Confirm the assigned process and version before evaluating each checkpoint. Coordinate supported downstream interactions with fulfillment and integration owners and manually inspect expected waits, branches, pauses, status, next steps, and business outcomes using correlated evidence. Test a nonmatching order and representative existing flows. Use new controlled orders; do not assume deployment changes existing instances or apply blanket cancellation and resubmission to recover earlier orders.
13. If assignment differs, inspect actual inputs and published rule behavior. For a stalled step, compare observed responses or events with exit and pause expectations. For unexpected business actions, stop further tests and inspect step/rule configuration and correlated downstream evidence. Capture tenant release, timestamp and time zone, exact error, process/version/step, order/line, and expected versus actual behavior. Define supported recovery with the relevant owners before retrying work that could duplicate business actions.
14. For restoration, stop test submissions and inventory affected instances. Have the owners identify the prior working process, deployment, and assignment setup. Restore future-order routing through the supported assignment procedure, coordinating activation/publication for changed rules. Restore or supersede custom definitions through supported version/deployment procedures and restore separately changed shared setup through its owner. Do not assume selecting an older definition restores runtime behavior or that a universal undeploy, reject, deactivate, or replay sequence exists. Record the supported recovery action and business impact, verify a fresh controlled order, and review active and completed instances individually. Do not delete a deployed process with active references or equate configuration restoration with reversal of fulfillment transactions.

## Manual validation guidance

Start each case as **Not Executed**. Mark irrelevant cases **Not Applicable** with a reason and expand coverage for specialized flows before acceptance. Distinguish review-only findings from changes and tests that were not performed.

| Case | Manual check | Acceptance criterion |
| --- | --- | --- |
| OP01 | Reopen the saved definition. | Header, steps, rules, copied rule-set name where applicable, and status conditions match the approved design. |
| OP02 | Inspect release validation. | Blocking errors are resolved and warnings assessed and recorded. |
| OP03 | Verify deployment evidence. | The exact target process/version has a confirmed successful outcome. |
| OP04 | Submit a matching controlled line. | Actual assignment uses the intended process/version. |
| OP05 | Submit a nonmatching controlled line. | Actual assignment follows the expected existing route. |
| OP06 | Observe the main fulfillment path. | Checkpoints and correlated downstream outcomes meet predefined expectations. |
| OP07 | Observe applicable branches, waits, and pauses. | Alternate paths and progression criteria behave as designed. |
| OP08 | Manually test a supported revision or cancellation. | Change behavior matches the approved compensation design. |
| OP09 | Observe an approved controlled failure and recovery. | The error is observable and supported recovery avoids unintended duplicate work. |
| OP10 | Test representative existing flows sharing configuration. | Expected prior behavior is retained. |
| OP11 | Test a fresh order after restoration. | Actual assignment and downstream behavior follow the restored working configuration. |

For each executed case, retain the operator, timestamp and time zone, environment/release, source and target/version, setup captures, release/deployment outcome, assignment evidence, actual process/version/step, order/revision/line, applicable correlated integration evidence, expected and observed results, outcome, and defect reference in the approved change record. Mask credentials and sensitive customer data. Record **Pass**, **Fail**, or **Blocked**; use **Blocked** when access, missing data, deployment, dependencies, or required response evidence prevent evaluation. Assign defects and blockers to owners, document rollback status and affected-instance disposition, and have the functional owner record acceptance or required follow-up based on actual results.
