# Manage Processing Constraints

- **Task code:** `DOO_MANAGE_PROCESS_CONSTRAINTS`
- **Purpose:** Review and maintain rules that control who can change an order, which operation is allowed, and when it is allowed, then manually verify both prohibited and permitted changes.
- **Execution rule:** The user completes the approved change manually in Oracle Fusion **Setup and Maintenance**, on **Manage Processing Constraints** and the applicable constraint-entity page, monitors required package generation through **Scheduled Processes**, and performs manual validation in the tenant's **Order Management** user interface, with no API, import, automated configuration, or browser automation.

Use the [standard shared manual workflow](../../../../shared/common/manual-tasks/SKILL.md).

Provide manual steps directly from this task using the user’s supplied values. Stay within the documented guidance, identify missing details, and do not create separate guides or project artifacts solely to explain the steps.

## Manual steps

1. Confirm the approved change reference, environment and tenant release, functional and security owners, execution path, constraint name/display name, entity, operation, exact attribute, record set, validation rule set, conditions/grouping/inversion, role scope and exclusions, expected message, and rollback owner. Choose review only, reuse existing validation, create custom validation, or maintain approved editable custom setup. Start in nonproduction and confirm setup, scheduled-process monitoring, and test-order access. Verify applicability of the supplied procedure to your tenant release and available controls; resolve missing values before editing.
2. Define the intended restriction in plain language, including the action, field, triggering state, and affected users. Inventory other constraints that could reject the test and consumers of shared record or validation sets. Confirm effective test-user roles with the security owner, including multiple-role membership. Prepare separate controlled orders or revisions for prohibited, permitted, and regression cases and agree on the fulfillment checkpoint with its owner. Do not disable predefined controls to force fulfillment.
3. Open **Setup and Maintenance** and search for **Manage Processing Constraints** using the tenant's available task-search route. Locate the exact constraint and capture entity, operation, target attribute, enabled state, conditions, messages, role assignments, referenced definitions, and other consumers as baseline evidence. If unavailable, verify setup access and search context. For review-only work, document the observed restriction and proceed to applicable manual validation without editing.
4. Review scope carefully before changing configuration: a blank attribute can restrict the whole entity, and a conditionless constraint evaluates as true. Predefined validation rule sets cannot be edited or deleted. Do not use a tilde (`~`) in validation-rule-set values. Select constraint names deliberately because names containing **GTM**, **PAYMENT**, or **PRICING** can affect validation context. Do not select a similarly named header or line attribute as a substitute.
5. If the precise attribute is unavailable, distinguish predefined **View** entities, such as Order Header, Order Line, and Order Fulfillment Line, from **Process** entities tied to process/task/service context, which can also be custom. For the approved view-attribute change, open **Manage Constraint Entities**, search with **Entity Type = Equals View Entity**, select the correct entity, and in **Attribute Details** enable **Constraint Enabled** for the intended field where supported. Save using the available tenant control, return to **Manage Processing Constraints**, and generate packages as described below to refresh availability.
6. Reuse suitable existing record and validation sets where they meet the design. Only if custom definitions are approved, select **Record Sets > Actions > Add Row**, enter **Name**, **Description**, **Short Name**, and **Entity**, and add the approved grouping **Attribute Name** in the details. **Save**, select **Generate Packages**, and verify successful completion before continuing. Then select **Validation Rule Sets > Actions > Add Row**, enter the approved identity, **Validation Type = Table**, and **Entity**. Add details using **Attribute Name**, **Validation Operation**, and **Value String**; save, generate again, and verify completion. Reopen and compare stored values with the design. Changes to shared sets affect other consumers.
7. For an approved new constraint, select **Constraints > Actions > Add Row**. Enter the approved name and display name, **Constraint Entity**, **Constrained Operation**, **Attribute Name**, and **Enabled** state. The supplied Inventory Management example uses **Order Fulfillment Line**, **Update**, and **Warehouse**, enabled, with the illustrative names **Inventory Management Constraint** and **Constrain According to Status in Inventory Management**. Use these only when they match the approved restriction; retain the specific attribute to avoid an unintended entity-wide restriction. For maintenance, change only the approved supported editable custom values.
8. In **Details > Conditions**, select **Actions > Add Row** and enter the approved condition. For the Warehouse example, **Group Number = 10**, **Validation Entity = Order Fulfillment Line**, **Validation Rule Set = Fulfillment Line is Picked or Staged**, and **Record Set = Fulfillment Line Default Record Set**. Enter an approved **Message** explaining the blocked change. For custom logic, **Invert Validation Rule Set** reverses the result and a shared **Group Number** combines AND conditions. Define and test a truth table for complex grouping rather than inferring behavior from row order.
9. Open **Applicable Roles** and apply the approved scope. The supplied all-user example selects **All Roles**, then **Save**; use narrower applicability or exclusions only where explicitly approved. Have the security owner verify effective memberships and exceptions before testing. Review entity, operation, attribute, conditions, message, role scope, and all pending shared changes before generation.
10. Save the completed table-based setup and manually select **Generate Packages**. This submits **Generate Constraint Packages** and deploys enabled constraints, affecting enabled setup beyond the selected row. Capture the request ID and monitor that exact request in **Scheduled Processes**. Retain successful completion evidence before runtime testing, then reopen the target and compare it with the approved change. Submission alone does not establish success. If it fails, retain messages/output and setup differences and involve the configuration owner before repeating generation. Arrange regeneration immediately after a release update when custom or modified constraints are used, after confirming applicability with the owner.
11. In the tenant's **Order Management** work area, create and submit a controlled order for the approved inventory flow. Record order, revision, fulfillment line, Warehouse, and downstream references. Have the inventory owner confirm the picking or staging checkpoint for the example. Sign in as the intended affected user and record effective role scope. Through the supported order revision or edit flow, attempt the planned Warehouse change, record actual navigation and the validation point, and capture the rejection/message. Requery to confirm the prohibited value did not persist and inspect downstream consistency. A rejection from another constraint or unrelated mandatory field does not validate this rule.
12. On a separate controlled order before the triggering checkpoint, attempt the same operation with the same user and other prerequisites satisfied. Confirm that this constraint does not reject it, assess other validation separately, and, if the full business flow permits, complete the change and inspect the saved value and downstream effect. For role-specific scope, repeat with the intended unaffected user after confirming effective roles. For multi-line actions, inspect each line's outcome; an aggregate warning may replace repeated custom messages.
13. If saved setup has no expected effect, check generation success, exact target, entity, operation, observed state, and effective roles. If too many changes are blocked, inspect blank attributes, absent conditions, grouping, inversion, and shared sets. For unexpected roles or messages, verify effective memberships/exclusions and identify the actual rejecting constraint. Retain tenant release, timestamp and time zone, generation request ID, constraint identity, exact error, role scope, order/line, and expected versus actual results.
14. For restoration, stop further test submissions and identify affected executions. Restore supported editable custom values, conditions, and roles from baseline. Disable a newly introduced custom constraint only when that is the agreed restoration action through supported UI controls; leave unrelated predefined controls unchanged. Restore shared sets only after reviewing other consumers. Save, regenerate, retain successful request evidence, and run fresh prohibited and permitted checks. Review affected orders individually; restored configuration does not reverse earlier successful changes or retry rejected submissions. Do not assume deleting a referenced setup record is a valid restoration method.

## Manual validation guidance

Start each case as **Not Executed**. Mark irrelevant cases **Not Applicable** with a reason, and distinguish review-only findings from unperformed setup changes or runtime tests. These checks establish behavior in the tested Fusion UI context only.

| Case | Manual check | Acceptance criterion |
| --- | --- | --- |
| PC01 | Reopen saved configuration. | Entity, operation, attribute, conditions, message, enabled state, and role scope match the approved change. |
| PC02 | Inspect the package-generation request. | The exact request completed successfully and evidence is retained. |
| PC03 | Attempt the prohibited change at the triggering state. | The intended constraint rejects it for the expected reason and the value does not persist. |
| PC04 | Attempt the same change outside the triggering state. | This constraint behaves as defined; unrelated validations are assessed separately. |
| PC05 | Test affected and unaffected users. | Effective role memberships and exclusions produce the approved behavior. |
| PC06 | Test unrelated editable fields. | The custom rule does not accidentally broaden the restriction. |
| PC07 | Exercise applicable grouping and inversion combinations. | Observations match the approved truth table. |
| PC08 | Test representative consumers of shared definitions. | Expected existing behavior is retained. |
| PC09 | Inspect a mixed eligible/constrained multi-line action. | Each line receives the expected handling, accounting for aggregate warnings. |
| PC10 | After restoration and successful regeneration, use fresh controlled orders. | Baseline setup passes both prohibited and permitted checks. |

Retain the case ID, operator, timestamp and time zone, environment/release, before-and-after setup, constraint and referenced-set identities, effective test-role scope, generation request ID/outcome, order/revision/line, expected and actual results, displayed messages, persistence checks, and downstream evidence in the approved change record. Record **Pass**, **Fail**, or **Blocked**; use **Blocked** when access, missing data, generation, or an unmet dependency prevents evaluation. Assign defects and blockers to owners, document rollback status and affected-order disposition, and have the functional owner record acceptance or required follow-up based on observed results.
