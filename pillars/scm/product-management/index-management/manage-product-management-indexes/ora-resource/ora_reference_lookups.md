## Source Provenance

The developer confirmed during the skill audit follow-up that
`indexManagementMetadata` and `indexAvailableAttributes` were discovered through
observed application behavior. The endpoint definitions below are retained as
developer-provided, application-observed guidance. This statement records their
discovery source; it does not claim a published Oracle API specification or
establish Oracle support status.

The observed Fusion release/build and a retained request/response capture were
not supplied with this clarification. No release-specific verification is
claimed. Runtime use follows the existing metadata validation and failure rules.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Read-semantic metadata POST lookups and Task Hook | Execute the declared indexManagementMetadata and indexAvailableAttributes POST lookups through core.fusion-api.rest-api-client in the active preflight before Task Hook validation. Retain complete responses in host memory bound to environment, canonical index and unchanged request SHA-256. Task Hook consumes that same evidence without issuing POST through the core GET lookup hook. Missing, incomplete, stale or mismatched context blocks preview and requires fresh preflight and Task Hook validation. Do not reconstruct evidence from chat or copy Core internal envelopes into pillar artifacts. After approval use Core retained-artifact integrity checks without repeating metadata or task validation. |
| Registered business-object metadata is unavailable or incomplete | Stop before sample generation or import planning and report the failed metadata stage without substituting another endpoint or business object. |
| User-provided index name is supplied | Use resolve_product_management_index_code before calling indexAvailableAttributes. It may match exactly against LookupCode or Meaning, but only the resolver's unique returned LookupCode may be used as IndexName in later requests. |
| Index scope is incomplete | Resolve supplied names or codes; present one unique scope candidate for confirmation. Request enough name-or-code context to distinguish multiple candidates; never require the user to know codes. |
| Indexed attribute is being removed | After canonical, seeded and complete existing-index lookups, use resolve_existing_product_management_es_indexed_attribute to resolve all original name/code/subtype selectors and any supplied ID together. Preserve the original request and store resolved names, codes, subtype and backend ID separately. Do not require user-supplied names or use indexAvailableAttributes to resolve DELETE. Available metadata is still allowed for a separate missing seeded POST candidate. |
| Available-attribute validation is unavailable, ambiguous, or incomplete for an unsatisfied request | Stop before POST payload preparation and import planning; do not infer an attribute code or target context. Already-indexed matches use verified existing evidence and do not require this lookup. |
| Seeded metadata is unavailable or malformed | Stop before addition-delta calculation and import planning; do not infer seeded attributes. |
| Existing indexed-attribute lookup is unavailable or malformed | Stop before addition-delta calculation and import planning; do not assume an attribute is absent. |
| A blocked accepted load has no authorized saved failure report | Use only the declared core.data-loader user-requested status workflow for the original accepted Request ID and verified environment. Normalize confirmed status in memory with immutable request/index/ID bindings and user_requested_status_check=true. Load reconciliation may omit a report artifact reference; do not create a core failure report to continue, reconstruct details from chat, poll automatically or resubmit. |
| A user-requested terminal Data Loader status is successful | For an already blocked accepted request, first validate reconciliation evidence for the original immutable invocation; never restart or resubmit. Invoke verify_loaded_index_attribute_delta, persist readback_verified only after every submitted change verifies, then prepare the ESS approval payload in the same response. |
