## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| LIST succeeds with records | Return the bounded items collection, hasMore, and totalItems when requested; record effective read success. |
| LIST succeeds with no records | Return an empty list and hasMore false; record effective read success. |
| GET succeeds | Return the record and record effective read success for the exact ID. |
| GET returns 404 | Return not found without inferring authorization failure or another record identity. |
| QUERY succeeds with records | Return items up to collection.limit, hasMore, totalItems when requested, every applied filter, requested content artifacts, and the applied sort or service-order disclosure. |
| QUERY succeeds with no records | Return an empty list and record effective read success without weakening the filter. |
| A LIST request explicitly says Sales Play or Sales Plays as a record type | Normalize sales_play_type to SALES_PLAY and pass raw $filter=((salesPlayType = 'SALES_PLAY')). |
| A LIST request explicitly says content bundle, content bundles, content packet, content packets, bundle, or packet | Normalize sales_play_type to CONTENT_BUNDLE and pass raw $filter=((salesPlayType = 'CONTENT_BUNDLE')). |
| A QUERY request explicitly identifies SALES_PLAY or CONTENT_BUNDLE | Add salesPlayType = 'SALES_PLAY' or salesPlayType = 'CONTENT_BUNDLE' to collection.filter; do not copy the LIST $filter template or use a root request property. |
| A QUERY request explicitly identifies DRAFT, ACTIVE, or ARCHIVE | Add status = 'DRAFT', status = 'ACTIVE', or status = 'ARCHIVE' to collection.filter; preserve it with every other requested predicate using lowercase and. |
| The request does not distinguish a record type | Do not add a salesPlayType predicate; include salesPlayType in each returned record so the mixed result remains distinguishable. |
| GET returns a salesPlayType different from the explicitly expected type | Return the exact-ID record with a type-mismatch diagnostic; do not replace it with another record. |
| CONTENT_SEARCH returns HTTP 2xx with an unambiguous content result | Return the sanitized response and WORKING_WITH_RESULTS for the exact acting user, question, and Sales Play ID. |
| CONTENT_SEARCH returns HTTP 2xx without an unambiguous content result | Return the sanitized response and WORKING_NO_RESULTS; do not infer missing authorization or claim content relevance. |
| CONTENT_SEARCH returns HTTP 403 after one cache-managed refresh | Return AUTHORIZATION_FAILED and direct the user to the Sales Play Consumer user-group and Sales Force Automation department policies; do not infer which policy is missing. |
| A natural-language read request contains supported predicates, projections, content accessors, bounds, pagination, a total-count request, ordering, or an effective date | Translate every explicit constraint into the corresponding documented LIST parameter, GET parameter, QUERY collection.filter or body field, or $effectiveDate parameter; derive intent from the complete request rather than matching a canned phrase. |
| A LIST request is passed to the shared BOSS client | Pass raw key=value query arguments and let the client URL-encode them once; reject pre-encoded or OData-style type filters before the call. |
| A LIST request asks for first or top N records without an order | Set $limit to the bounded positive N, use offset zero unless another offset is requested, preserve service order, and disclose that no explicit sort was applied. |
| A LIST request explicitly asks for descending creation time | Pass raw $sortBy=timeCreated:desc after validating timeCreated as sortable. |
| A QUERY contains multiple predicates | Preserve every supported predicate in collection.filter or the applicable accessor query; do not drop, broaden, or weaken a condition. |
| A QUERY asks for the first or top N records without an order | Set collection.limit to the bounded positive N, preserve service order, and disclose that no explicit sort was applied. |
| A QUERY requests ordering | Set collection.sortBy only when the sortable field and direction are explicit or unambiguous; otherwise stop and request one short clarification. |
| A request includes an unsupported or ambiguous field, accessor, subtype, enum, operator, predicate, or ordering choice | Stop before the API call and identify the unsupported part or required clarification; do not silently approximate the request. |
| BOSS LIST or GET returns 403 after its one cache-managed refresh, or QUERY returns 403 without an automatic refresh or retry | Return an authorization or privilege failure; do not infer the missing role, permission group, or data security policy. |
| A mutation operation is requested | Return unsupported and do not invoke a write endpoint; the exact POST salesPlays/$query and POST /api/knowledge-management/v2/contentIntelligence operations are semantic reads, not mutations. |
| A response contains more rows than the approved bound | Return only the approved bound and disclose whether more records are available. |
