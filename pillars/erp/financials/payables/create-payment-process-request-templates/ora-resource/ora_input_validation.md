## Package validation

Bind the manifest to the explicitly selected Fusion environment: its environment
must exactly match the package `ProcessEnv`. Keep the authentication-profile
label separate; never derive a pod identity by stripping a profile suffix.
Require a credential-free HTTPS origin with a valid host and optional port,
without a path (including `/`), query or fragment. This syntax check does not
establish the origin's relationship to the selected environment; the invoking
workflow must establish that relationship independently.

Require `template_only` to be a Boolean. `true` requires an archive without data
rows; `false` permits an empty full export. An empty archive is not proof of its
export mode.

Before publishing package outputs or returning a no-op, check archive identity,
metadata coverage, ordered headers, row widths, keys, schema fingerprints and
source compatibility. Enforce archive size and compression-ratio limits; reject
unsafe paths and nonregular members. Reject output aliases, links and overwrites
before publishing. Follow [local publication and recovery](ora_error_handling.md#local-publication-and-recovery)
for staged output handling and failure diagnostics.

## Validation Responsibility

| Input or operation | Preparation rule | Fusion responsibility |
|---|---|---|
| Supported mapped field | Apply its declared type, fixed choices, requiredness, related-value rules and package/identity checks. Use normal candidate preview and Data Loader approval; no extra uncertainty acceptance is required merely because an internal implementation detail is unverified. | Apply configured eligibility and import rules; report errors and verify saved values through the selected readback workflow. |
| Declared REST reference check | One or more exact matching rows pass, including duplicates. Keep the field/value/operation-bound receipt. A successful no-match requires correction; authentication or transport failures mean validation is unavailable. | Retain application-specific eligibility checks. Do not require helper-revision, duplicate-selection or enablement proof after the declared REST check passes. |
| Designated direct user input | Preserve Transaction Calendar, First Approver, Funding Card Account and Bank Conversion Rate Type as supplied under the acceptable-input policy. Apply only the separately declared structural rules and CSV mapping. | Determine acceptance and persistence for mapped values. Direct input handling does not supply a missing CSV column. |
| Unverified direct field write | Only OrgId, TransferPriority and legal-entity display Name have the declared field-specific UPDATE exception. Require its exact field/operation acceptance and retain the preview warning; do not generalize it to create. | Validate the approved submission; read back the intended value before claiming persistence. No automatic retry. |
| Selection identity | Create/add membership using the declared key and parent context. Ordinary updates cannot rename child keys or remove/replace individual selections. Explicit documented ALL setter effects remain supported. | Import the approved operation; a different key must not be represented as an update of the original member. |
| Missing mapping or unsupported operation | Stop only the affected requested operation and explain the specific limit. Retain an unmapped input in the request and preview; never invent a CSV column or silently omit a requested effect. | No submission can establish support for an invented mapping. |

Do not require proof of internal setter order, a consumed helper revision or future saved values before ordinary valid preparation. Disclose known effects and separate local validation, Fusion acceptance and persisted-state verification.
