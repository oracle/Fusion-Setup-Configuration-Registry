# Assisted customer evidence review


This route evaluates evidence already supplied in the task context. It does not
run Publisher SQL from a task node or substitute a private Fusion client. The
initial developer campaign may use reviewed read-only FSCM Publisher results.
The evaluator can also consume the raw supported API collections below. Missing
required evidence remains unresolved; neither route invents a passed observation.

## Supported API evidence for existing targets

Select the read-only collection route in [REST reconciliation](rest-reconciliation.md).
The combined live snapshot uses unchanged core transport; offline SOAP replay uses
the task-owned parser. See [governed read routes](governed-read-routes.md). The following is the
required interpretation contract for retained/synthetic evidence, not permission
to collect through the former SOAP extension. The selected route retains
source-code resolution, historical/current reference completeness, independent
number searches, privileges and freshness.
Then evaluate `customer_api_target_review.analyze` with a candidate/environment/
operation/collection-bound `ar-customer-api-target-plan-v1` declaring the seven
entity intents. Every existing owner, number and parent/purpose/set relationship
must agree. Requested before-value differences are expected for updates and do
not turn matching targets into missing records. Source-reference ambiguity still
requires review. Retain the raw captures and explicit plan, not just a PASS summary.

This existing-target component does not qualify new/partial hierarchies; those
remain subject to their separate target review. It does not restrict product scope
to updates or authorize an import. SQL is never a prerequisite for this API route.
Field effects, requested DFF limits and post-import outcomes remain separate.

## Supplied detailed developer evidence

Before ARCU.MATCH, supply the exact candidate, environment and operation intent,
plus raw [identity](identity-evidence.md), [before-ownership](ownership-evidence.md)
and [target-plan](target-evidence.md) documents. Retain their query text, result
capture, environment, database date and completeness/provenance records in the
private campaign/project workspace. Never package customer records or environment
identifiers as reusable skill defaults.

Review the source before accepting the documents: exact source-name resolution,
all seven source-reference queries, complete number-collision queries without
status or expected-parent filtering, and ownership queries for every returned
target ID. Preserve ambiguity, inactive references and nulls. A zero-match outer
join sentinel represents an empty record list only when the explicit match count
is zero; an omitted result or a truncated preview is unknown. Before import,
refresh time-sensitive observations when changed state or elapsed work makes
them unreliable. Do not invent a universal freshness interval.

Recompute `customer_target_review.analyze(candidate, operation, environment,
before_identity, before_ownership, target_plan)`. The `resolved` transition requires
`target_intent_observations_consistent` and a reviewed source/completeness record.
Any missing input, exception or conflicting finding takes `blocked`; retain the
finding. The composed campaign reviewer can carry the same evidence but does not
authorize this transition merely because some requested after-values match.

This pre-import result establishes only consistency of proposed targets with
observations. ARCU.DESIGN must still review selected field differences, blank and
default effects, shared/sibling effects and source-supported operation ownership.
Named business-validation uncertainty can be disclosed for loader reliance.
Missing identity, routing, intended effects or approval is not converted into
loader acceptance. The execution gate still requires its central handoff and
complete post-import readback contract.

After submission use fresh evidence and the campaign reviewer; before-state
documents cannot substitute for after-state documents. Compare every requested
field and actual operation effects, retain partial persistence and unknown
asynchronous tax completion, and bind observations to the central attempt.
Keep business outcome separate from Journey synchronization. API components must
be composed and verified for the actual candidate; the existing detailed developer
route does not establish that every runtime scenario has been qualified.
