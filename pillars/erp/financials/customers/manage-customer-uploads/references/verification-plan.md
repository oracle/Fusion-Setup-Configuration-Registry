# Customers import verification plan


Generate the exact candidate's plan with `customer_campaign_review.py plan`.
The plan binds the archive, environment and operation and partitions every row's
87 columns into requested-value and omitted-field effect checks. Its collection
contract separates evidence available before preview from evidence obtained only
after submission. Generating a plan proves neither that the queries work nor that
the evidence has been captured or reviewed.

For the functional journey, use the plan's `runtime_business_outcome_scope` and
[business-outcome reconciliation](business-outcome-reconciliation.md). Every
supplied DFF field remains required. Unused hidden storage and unrelated history
are disclosed, not unconditional blockers. The detailed supplied-evidence
collection shapes below describe the deeper developer verification route; they
must not be imposed on the implementor or substituted for supported runtime reads.

The initial developer-test campaign uses assisted review of supplied read-only
FSCM Publisher/JDBC evidence and retained core Data Loader outputs. This SQL
access is not part of the functional journey and must not become an implementor
prerequisite. Developer-test success cannot qualify supported runtime reconciliation.
Use the approved authentication
and project workflow. The task nodes do not execute SQL, introduce another
Fusion client, or substitute a direct import route. The
[reusable API collector](rest-reconciliation.md) now automates the qualified
source-reference, selected hierarchy/location and receipt observations through
central clients. Composition of required identity, requested values, relevant
effects and attempt evidence remains a separate dependency; a passing value
component alone does not make the execution gate pass.

## Detailed developer collection before preview

Review the exact candidate's intended create/update/reuse effects and retain the
following before-state observations with query text, scope, capture time,
database date, completeness and provenance:

| Evidence | Required scope and review |
|---|---|
| Identity and target plan | Exact source-name resolution, all seven entity references and all number-collision queries, including inactive/history matches; no expected-parent filter that hides a collision |
| Ownership | Every observed target's actual parent, purpose and set relationships |
| Direct values | All 75 mapped fields for observed entities, including omitted fields and all account DFF segments, using the complete effect-value projections |
| Supporting inventories | Organization-profile history and all party-site uses for each observed party, including sibling sites |
| Account-site effects | For affected existing accounts, retain all site uses and account-site Bill-to/Ship-to/Market flags separately from technical timestamps/batch stamps; the supporting helper does not cover this projection |
| Profile, receipt, tax and bill-to baselines | Review the inventories and fields relevant to expected defaults, assignment changes, tax callbacks and cross-site links; selected-value matches alone cannot establish these effects |
| Expected effects | One reviewed intent per row/entity, requested changes and treatment of blanks/defaults; retain unresolved business eligibility separately |

No record found for a source reference does not prove the physical entity did
not exist. When no before-state entity ID is available, retain that fact and the
scoped negative observations. Do not manufacture an empty inventory using an ID
obtained after import. Plan a separate creation/reuse review using retained
target matches, available base-record audit data and attempt lineage; disclose
where these cannot rule out pre-existing or concurrently created entities.

Registration and core handoff evidence follow [registration binding](registration-evidence.md).
Missing identity, intended effects or central routing cannot be accepted as a
business-rule uncertainty. Eligible loader-validation uncertainty remains named
in the exact candidate's normal decision. The plan requires no future request ID,
post-import result or Journey completion before preview.

## Detailed developer collection after the one governed submission

Use the same candidate and retain the actual core initiation response. Collect
core status through the declared central route and apply
[attempt association](attempt-association.md). Keep Data Loader initiation,
dataset, Run Book, content, interface request, product upload request and batch
identifiers distinct. Missing association stays unresolved; do not select a
plausible ID or resubmit to obtain a cleaner result.

Collect staging evidence for the actual interface scope, preserving every status,
row and stamp. Verify [request scope](request-evidence.md) and separately review
candidate-to-staging lineage. FILE_RECORD_NUM is not necessarily a CSV row index.
Capture persisted evidence even after a failed or partial process:

| Evidence | Reviewer and remaining responsibility |
|---|---|
| Identity, ownership and requested values | Recompute the identity, ownership and value reviewers from fresh raw observations; retain missing and conflicting entities alongside successful rows |
| Profiles and reference sets | Profile/set reviewer, then review defaults, effective history and actual create/update/reuse effects separately |
| Receipt assignments | Requested-field reviewer plus complete before/after account assignment inventories; blank method input does not prove no assignment effect |
| Bill-to relationships | Resolve supplied references and compare actual links; review blank-input effects against before/after values separately |
| Tax profiles | Compare requested registration and preserve complete scoped profiles, ambiguity and callback evidence; blank registration does not prove absence of a profile, and a pending callback is not success |
| Omitted fields, DFFs and sibling effects | Complete direct-value and supporting inventories; explain every observed change outside the requested values |

The composed reviewer reports selected observations. Manual supporting reviews
are retained separately; they are not extra keys silently accepted by the raw
evidence bundle. The generated plan's `mandatory_evidence` and
`additional_requested_evidence` describe helper inputs, not all completion
requirements. For this deeper developer route, follow the full
`collection_contract`, including separate reviews. Functional readiness uses
the candidate's runtime scope instead.

## Decision and recovery

Report process state, per-row/entity business observations, unverified effects
and Journey synchronization separately. A successful process or matching input
values cannot close unresolved creation, default, partial-persistence or lineage
findings. If evidence is missing, report incomplete verification and the next
read-only check; do not infer rollback or completed import.

On timeout or lost response, continue status inspection for the same retained
attempt. For partial failure, retain successful targets and errors before designing
a correction. A changed artifact, intent, scope, registration or arguments needs
a fresh preview and normal approval. No automatic retry, inverse import or
staging purge is a business rollback. Journey completion remains governed by Run
Book and its separate completion decision.

This plan defines collection responsibilities; it does not close the remaining
central execution gate, prove privilege availability or make the task merge-ready.
