# Manage Control Budgets Input Validation

## Validation unit boundary

Apply the Required Groups and Field Validation checks for every requested Control Budget header, its budget segments, and their assigned trees as the first request-wide phase. Collect all independently checkable failures across budgets in prompt order before the gate decision. Give each source segment and selected tree separate check IDs so an invalid segment marks only its own dependent tree `not_evaluated`; independently check a selected tree on a different valid segment. The 1-to-30 segment-count rule still runs separately for each budget before its lookups and template export; when it fails, collect the remaining direct-input failures and mark dependent lookup checks `not_evaluated` with the missing prerequisite. If any Control Budget fails, report all budgets' first-phase findings together and do not apply Supplemental Rule Validation to any budget.

After every requested Control Budget passes the first gate, apply the Supplemental Rule Required Groups and Supplemental Rule Validation checks to **all** supplied rules across budgets. Check each rule header, Budget Segment Filters, Additional Segment Filters, and Transaction Attribute Filters, including every supplied Specific value. Independently apply the Revenue and Override checks below to every requested rule, even when another group's findings exist. Collect every independent failure in all three requested groups before the final package gate decides; no group's success is a prerequisite for checking another. A failed prerequisite prevents only dependent checks; report each such check as `not_evaluated` with the prerequisite. Preserve each named Check and its existing terminal-reason mapping; record all findings in one report even though `actualReason` contains only one deterministic primary reason.

## Required Groups

The optional Override notification choices are Control Budget header fields.
Normalize each supplied enabled/disabled choice independently to Y/N for
`NoOverridesNotifyFlag` and `OverridesTakenNotifyFlag` in
`ORA_XCC_CONTROL_BUDGET.csv`. Apply N only when the individual choice is omitted;
an explicit Y remains Y. Reject a malformed explicit flag under the header
validation rather than treating it as an omitted choice. Retain separate
choices for each requested budget without deriving either notification from
Allow Overrides, the rule EnabledFlag, or user assignments.

## Supplemental Rule Validation

Apply these checks only after the request-wide Control Budget phase passes and only when Supplemental Rules are supplied. Evaluate every rule and every independently checkable filter/value before returning the Supplemental Rule phase result. Oracle Financials 26C defines them as exceptions to header control level and tolerance. When multiple rules match a transaction, the highest control level and lowest tolerance apply; the skill must disclose overlapping rules in the preview rather than silently choose one. Cash and procure-to-pay budgets differ in whether supplemental rules affect a later budget-balance import; do not confuse that behavior with the FSM setup import.

## Exact Numeric Preparation Inputs

For Revenue fixed amounts and funding percentages, and Override rule/header
amounts, preserve the original user-entered decimal text in normalized JSON
strings. Do not first convert through a binary float. The preparation CLIs accept
JSON numeric tokens losslessly, retaining fractional precision, trailing zeros,
and exponent spelling for CSV output without turning numeric tokens into valid
account, journal, user, or other text values. Programmatic calls accept decimal
strings, integers, and `Decimal` values and reject binary `float` financial
values. Re-normalize a rejected float from the original input; casting an already
rounded float to text does not restore precision. Existing positivity, finite
number, exact-total, and source-compatible cap checks still apply.
