# Manage Budgetary Control Dependency Readiness

## Required Dependency Order

| Sequence | Dependency | What Must Happen |
|---|---|---|
| 1 | Enterprise Options | Include whenever present; validate its enterprise scope from evidence. |
| 2 | GL Attributes, then Enabled Ledger | Resolve the exact target ledger identity first. Follow the current same-task XML node order: when both representations are present, process GL Attributes before Enabled Ledger and keep their BC or EA attributes consistent. |
| 3 | Ledger children | Process segment values, cash accounts, and journal sources after Enabled Ledger. |
| 4 | Journal Category | Process only after the referenced journal source. |
| 5 | Business Unit and Function | Process Business Unit after Enabled Ledger and Business Function after Business Unit. |
| 6 | Transaction children | Process transaction source and transaction type after Business Function; process document type after transaction source. Project Accounting (`PROJECT_ACCOUNTING_BF` — Project Accounting) has no transaction type or subtype children; its transaction source and document rows are allowed only after Project Accounting Budgetary Control is enabled. |

## Dependency Classification

| Result Category | When Used | Can Run Lookup/Create? |
|---|---|---|
| Satisfied | Exact metadata, existing-object, and parent evidence are complete | Lookup yes; create only after approval |
| Technical lookup gap | Required internal code, metadata member, column, default, or identity is unresolved | Lookup yes; create no |
| Business decision | Existing definition differs or a requested update is not confirmed | Lookup yes; create no |
| Approval blocker | Immutable package is not explicitly approved | Lookup yes; create no |
