## Business-Unit Validation Procedure

Use `core.fusion-api.rest-api-client` through the active task workflow and its bound target environment. The supported contract is [Financials business units LOV](https://docs.oracle.com/en/cloud/saas/financials/26c/farfa/op-finbusinessunitslov-get.html). It exposes BU identity independently of an existing RSO row. Do not use `receivablesBusinessUnitsLOV` as the RSO identity prerequisite: its Receivables activity context and existing-system-options filtering do not establish create eligibility.

1. Resolve an exact name, or an explicitly supplied numeric ID, using `finBusinessUnitsLOV`. Treat a numeric-looking name as a name unless the user identifies it as an ID. Escape the query literal and URL-encode query parameters with the shared client; never concatenate unescaped business input. Require a successful response, one item, `count=1`, `hasMore=false`, and `offset=0`. Two items or more is ambiguous; one item with more pages is incomplete, not unique. A zero result means not resolved in this invocation, not proof of missing BU access.
2. Require nonblank BusinessUnitId and BusinessUnitName and `ActiveFlag=true`. If both name and ID were supplied they must identify the same row. Preserve the returned canonical name in the FSM package; do not insert physical IDs into BUName or manufacture an OrgId column.
3. For the target BU, require a primary ledger and default legal entity. Resolve the proposed LedgerName through `resolve_ledger` and compare its LedgerId to PrimaryLedgerId; stop a mismatch. Existing RSO is not evidence that a different requested ledger is valid. Activity BU fields require their own exact identity; do not require them to share the target's ledger.
4. Validate applicable business functions separately. For a Billing and Revenue Management target, repeat the exact identity query with `finder=ModuleIdFinder;ModuleId=30` and require the same unique active BU ID. Module 30 is the Billing function mapping owned by `erp.financials.organization-structures` (`ora-resource/ora_reference_lookups.md`). Preserve the existing conditional Cash Processing/reference-data requirements; do not impose Billing on an activity BU or infer all RSO eligibility from a generic identity lookup. A function-filter miss blocks that function requirement, not the claim that the BU exists.
5. Independently read the fresh successful same-target `AR_SYSTEM_OPTIONS` export and count exact canonical BUName matches. CREATE requires zero existing rows; UPDATE requires exactly one. Reject a duplicate create and a missing/ambiguous update before candidate generation. Apply this to every bulk row and reject repeated target keys. An absent export row means no exported RSO for that BU; it cannot validate a new BU's identity or business functions. An incomplete or wrong-target export cannot establish absence.
6. Retain the lookup and export fingerprints, target, time, requested name/ID, function filter, match counts, active flag and ledger comparison as prerequisite evidence. Retain normal account/rule validation, immutable preview and approval, FSM import, and fresh-export reconciliation. A read-only lookup or local Data Loader preview does not execute import-time business validation or guarantee import success. Never mark an unresolved lookup satisfied merely because the user asks to continue.

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| No supported public preflight path, but a complete Confirmed FSM import contract exists | Do not call internal components or invent a REST path. Continue static planning and bind the affected field's confirmed import contract and required inputs/context before immutable Data Loader preview and approval; confirm final resolution or validation from FSM import and reconciliation |
| Resolver contract is Partial, To collect, unsupported, or `TBD` | Block the affected field and request the missing contract evidence |
| Free-text reference | Use exact normalized matching, active/effective filters where supported, full pagination, and cardinality one; never select the first row |
| Resolver dependency | Resolve business unit, ledger/chart of accounts, and reference-data set before dependent activity, account, rule, source, or type lookups |
| Package evidence | Use only same-task export/template shape and verification evidence; do not copy physical IDs or current-data values into generated examples |
| Receipt | Record target, release, as-of time, normalized inputs, approved method/path, requested fields, match count, natural keys, receipt-only IDs, and redacted fingerprint |
