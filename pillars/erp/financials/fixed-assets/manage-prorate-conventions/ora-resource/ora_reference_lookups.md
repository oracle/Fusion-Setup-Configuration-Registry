## Existing-Date Retrieval

1. For update date comparison and audit preservation, acquire a fresh populated export for FA_MANAGE_PRORATE_CONVENTION directly through shared.setup-export.task-level-export with --data, the current project ID, Financials and Fixed Assets context, and the same configured target. Do not query BOSS for existing date rows or attempt date-child discovery. Save the export under the current project exports directory. Reuse an already-started export process rather than duplicate submission. Keep this data export separate from the create template/spec contract.
2. From FA_PRORATE_CONVENTION.csv require exactly one parent whose ProrateConventionCode equals the requested Name and whose SetCode equals the verified selected code. From ORA_FA_PRORATE_CONVENTION_DATE.csv select only rows whose FA_PRORATE_CONVENTION.ProrateConventionCode and FA_PRORATE_CONVENTION.SetCode match that exported parent. Read StartDate, EndDate and ProrateDate; preserve exact audit-field text from those same rows for update serialization. Do not map BOSS setId or its Boolean. The proposed business flag still uses supplied input or Standard Defaults.
3. Parse dates for comparison using the task business date contract; index by the exact exported parent plus date-only StartDate and EndDate. A complete export with no detail row for a proposed range means a new detail. Duplicate parent matches, duplicate ranges, conflicting values, malformed dates or unproven ownership block update preparation.
4. Record the export source, target, completion time, archive/process reference and completeness checks. Reuse only within the pending update on the same target. If the export fails or is incomplete, stop update preparation with its observed error and normal diagnostics. No import, repair or update is authorized by reading the export.

## Fiscal-Year Selection Rules

Apply [Fiscal-Year Lookup Freshness](#fiscal-year-lookup-freshness) before using retained evidence.

| Situation | What Happens |
|---|---|
| Exact name, including existing-ZIP validation | Complete name-filtered paging and retain exact case-sensitive fiscalYearName matches. Zero means invalid name. Never replace an invalid supplied name by cycle discovery or infer/change an archive's name. |
| Cycle-only discovery | Complete the unfiltered collection before selecting/listing names. Group by exact fiscalYearName; multiple years or duplicate rows are one candidate name. Do not invent month-extraction query syntax. |
| Match a fiscal-year cycle | Parse startDate/endDate as ISO date-only values. Every row of a nonempty name group must have the requested start/end months. Compare only month numbers; do not discard rows with another pair. Missing names, malformed dates, or startDate after endDate make discovery incomplete, not a no-match result. |
| Cycle-only create/update result after complete discovery | Zero matching names, including an empty collection, means no matching cycle. One resolves automatically; multiple use Most recently updated matching name. Do not ask to choose/confirm or show candidates unless requested. Retain the selected exact name for review. |
| Most recently updated matching name | Required for automatic selection among multiple matches, latest-for-cycle inquiries, and named last-updated information. Parse every relevant timeUpdated as an ISO timestamp with Z or an explicit offset; compare UTC instants. Per name, take the maximum across all its rows; among names choose the greatest maximum, with the last tied name encountered as tie-breaker. Missing/null/malformed/timezone-less values make comparison unavailable. Never rank by strings, averages, fiscal dates, timeCreated, or name spelling, or fall back to an older known candidate. Explicit-name/single-match convention validation and names-only lists require no ranking. |
| Inquiry lookup scope | A matching-name list uses cycle discovery; latest-for-cycle also uses timestamp ranking, even for one match. For latest-for-cycle when only a name is known and its cycle is not, first establish its consistent month pair by fresh exact-name lookup, then discover all names for that pair. A named last-updated question uses the exact-name rows and their per-name maximum; this alone cannot establish newest-for-cycle. |
| Explicit request to show matching fiscal years | Return distinct matches in ascending case-sensitive ordinal name order with the cycle; this is display order, not selection. Zero uses the period-specific error response. If list and create/update are explicitly combined, include the list and apply the operation's selection rule unless the user asks to choose first. |
| Exact name plus a cycle, including a later user-selected name | Apply the cycle test to all filtered rows. An existing name with different/mixed months returns name/cycle conflict, not invalid name; do not replace the name or drop the constraint. |
| Fetch years for the resolved name | After cycle selection, make a separate fully paged exact-name request using the Live Lookups contract; discovery rows cannot replace it. A supplied exact name's completed request already satisfies this step. Recheck any cycle constraint against all returned years. Names-only listing needs no second fetch. |
| Resolved create/update or existing-ZIP result | Preserve the exact returned name as Fiscal Year Name and normalize its filtered rows through Fiscal-year date context. Never serialize cycle text or invent a name. Apply Fiscal-year setup preservation in [Design Rules](ora_design_enforcement.md#design-rules). The normalized context supplies fiscal_year_date_rows to Generation Contract. |

## Lookup Execution Rules

| Situation | What Happens |
|---|---|
| Configured API connection | Read the [Core REST client](../../../../../../core/fusion-api/rest-api-client/SKILL.md) and its routed endpoint instructions. Use its default core/auth/fusionEnv.properties from the canonical FSCR repository; resolve paths there, not from the working directory or installed skill folder. Browser inventory is not connection preflight, and an open Fusion setup page is not required. Never substitute manual UI creation for this route. |
| Request delegation | Invoke the Core REST client's declared script from the canonical repository root for these GETs and raw query values via its BOSS route. Core delegates authentication to core.auth.fusion-oauth-authentication and owns token acquisition/cache/refresh and request/response handling. Target consistency follows Fiscal-Year Lookup Freshness. |
| Filter construction | Double embedded apostrophes in a supplied name before building the single-quoted filter literal, pass raw query key/value pairs to the shared client, and let the client URL-encode once. |
| Live collection pagination | Begin at offset 0, preserving each Live Lookups query on every page. If hasMore is true, advance by raw item count. If absent, continue after a full 25-item page and stop at the first short page. A zero/non-increasing next offset, malformed indicator, or missing expected page makes the lookup incomplete. Complete paging before consuming any result. |
| Repeated-page protection | Fingerprint each raw page as an order-independent multiset of canonical item content, including duplicate counts. Stop if a later page repeats an earlier fingerprint. |
| Fiscal-year date context | Normalize the completed exact-name matches: parse ISO date-only boundaries without timezone conversion; parse each non-null midyearStartDate inside its own inclusive interval. Group by exact startDate/endDate, retaining one interval with its single distinct non-null midpoint, or null if all copies are null. Conflicting non-null midpoints are a lookup gap. Return normalizedFiscalYearRows sorted by parsed startDate then endDate, retaining assetFiscalYear and dates. Keep duplicate evidence/raw counts separately. coverageStart/coverageEnd summarize first start/last end only; never use them as generation input or merge returned-year boundaries. |
| Request failure policy | Apply the read-only retry, authorization, and stop rules owned by ora_error_handling.md. |
| Evidence retention | Bind sanitized results to operation, resolved target identity/host, selector/constraint, and actual UTC start/completion times. Keep separate discovery/name-fetch completion, match counts, SetCode, normalized date context and summary bounds, paging evidence, and redacted failures. Keep candidate names and per-name/selected maximum timeUpdated when comparison/reporting requires them. Do not persist raw responses or unrelated discovery groups. Timestamps are evidence, not package audit/default values; Disclosure Rules owns user-facing timestamp wording. |

## Fiscal-Year Lookup Freshness

| Situation | What Happens |
|---|---|
| New create/update validation or explicit restart/revalidate request | Resolve the current configured target through the shared connection and perform fresh fiscal-year requests beginning at offset 0. For a cycle selector, rediscover all matching names and rerank before fetching the selected exact name; do not substitute a previously auto-selected name as user input. For an explicit exact name, fetch only that name and preserve its constraint. Old conversations, run files, exports, and completed lookups are historical evidence, not the current result, even when the target and input are unchanged. |
| Explicit latest, refresh, recheck, list, or last-updated question | Start a fresh inquiry on the current target using Inquiry lookup scope. Resolve references from retained selectors; ask only when scope is unclear. Asking when a past lookup ran uses its recorded evidence, not a new lookup. |
| Several conventions in one validation operation | A completed fresh lookup may serve identical selectors on the same resolved target within that operation. Do not reuse that snapshot as fresh evidence for a later independent request. Token-cache reuse through Core is independent of lookup freshness. |
| Continuing a pending workflow | Conversation State and Resume determines the retained selection. An unchanged approval or unrelated correction does not trigger discovery. Required revalidation uses fresh rows for that retained exact name, not cycle reranking; an explicit restart instead follows the new-validation rule. |
| Configured target changes | Re-resolve the target when starting or resuming validation and before handing a pending approval to its parent-owned step. If its identity or host differs from the evidence target, do not reuse target-bound lookup, export, package, or approval evidence. Preserve business input, invalidate affected readiness, and return through validation and the existing parent review gates for the new target. Never submit an old approved ZIP to the changed target. A change during paging makes the operation incomplete; do not combine pages from different targets. Accepted-submission status stays bound to the original submission target through its owner; do not rebind it or resubmit. |
| Evidence has no operation, target, or completion-time provenance, or a required refresh fails | It cannot establish current validity or newest selection. Obtain a fresh complete result, or use the owning lookup-failure response. Keep an older selection only as historical/pending-review context, never as a successful substitute for the failed current check. |
