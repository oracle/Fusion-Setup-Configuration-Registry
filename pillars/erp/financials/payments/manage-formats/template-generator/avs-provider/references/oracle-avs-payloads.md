# Oracle AVS Payload Reference

## XML-First Transformation Contract

Oracle Payments AVS transformations are XML-first even when the provider API is JSON/REST.

Request flow:

1. `Create_Ba_Ownr_Verif_Extract_1_0` generates Oracle generic request XML from the PL/SQL/view source.
2. The provider request XSLT transforms that generic XML into provider-shaped XML.
3. If the provider expects JSON, Oracle converts the provider-shaped XML into the JSON request body.

Response flow:

1. Oracle receives the provider response. If it is JSON, Oracle first converts it into XML.
2. The provider response XSLT transforms that converted provider-response XML into Oracle normalized response XML.
3. Oracle reads the normalized response fields to update bank-account and owner verification statuses.

Therefore, provider JSON examples should be treated as evidence for the XML serialization/deserialization shape, not as a reason to bypass XML. Draft and validate XSLT against XML inputs and XML outputs.

## Generic Request Shape

The Oracle Payments AVS request generated by `Create_Ba_Ownr_Verif_Extract_1_0` is rooted at:

```xml
<BankAccountVerificationRequest>
  <RequestId>...</RequestId>
  <PaymentSystemAccount>
    <AccountName>...</AccountName>
    <!-- payment-system account options may appear here -->
  </PaymentSystemAccount>
  <BankAccount>
    <BankAccountNumber>...</BankAccountNumber>
    <IBAN>...</IBAN>
    <BankAccountNumberElectronic>...</BankAccountNumberElectronic>
    <CountryCode>...</CountryCode>
    <BankName>...</BankName>
    <BankNumber>...</BankNumber>
    <BranchName>...</BranchName>
    <BranchNumber>...</BranchNumber>
    <EftSwiftCode>...</EftSwiftCode>
    <BranchType>...</BranchType>
  </BankAccount>
  <BankAccountOwner>
    <AccountOwnerName>...</AccountOwnerName>
    <OwnerFirstName>...</OwnerFirstName>
    <OwnerLastName>...</OwnerLastName>
    <OwnerPartyType>...</OwnerPartyType>
    <OwnerTaxId>...</OwnerTaxId>
    <PrimaryFlag>Y|N</PrimaryFlag>
  </BankAccountOwner>
</BankAccountVerificationRequest>
```

Use the actual view in the workspace as the source of truth. In the reviewed `iby_xml_temp_ba_verif_1_0_v.view`, `OwnerTaxId` is emitted from `OWNER_TAX_ID`, but the reviewed procedure declares `p_tax_id` without setting that view parameter. Flag this kind of gap rather than assuming the field is populated.

`OwnerPartyType` comes from `HZ_PARTIES.PARTY_TYPE` or a caller override. Existing templates commonly handle `PERSON` and `ORGANIZATION`, but the generic XML is not inherently limited to those values.

## Provider Request Pattern

Existing request templates transform the generic root into provider-shaped XML. The application may then convert that provider XML to JSON. Preserve local conventions unless the codebase shows otherwise:

```xml
<RequestMessage>
  <!-- provider request body fields -->
  <ExtraHints>
    <EXTRA_HEADERS>@header:Header-Name=value|@header:Other=value</EXTRA_HEADERS>
  </ExtraHints>
</RequestMessage>
```

The reviewed `JPM_AVS_Request.xml` seed uses pipe-delimited tokens such as
`@header:x-client-id=&BA_VAL_CLIENT_ID` (escape `&` as `&amp;` in XML).
Preserve the exact seeded form when following that integration. Do not strip or add
the `@header:` prefix based on a generic example. Before generating a different
HTTP/JSON profile, trace the deployed protocol's header-token consumer and XML/JSON
converter, or record the missing contract as a source gap. Seed syntax alone does
not prove another provider or deployed protocol accepts it. XML-only offline
profiles with no headers must say that this transport behavior was not exercised.

Map `RequestId` to provider correlation headers only if it can satisfy the provider's format rules. If an XSLT 1.0 template can only partially sanitize a value, document that assumption.

For JSON providers, design provider-shaped XML with predictable JSON conversion:

- Use element names that match the intended JSON property names unless the local converter requires a different naming convention.
- Use repeated sibling elements only when the converter is expected to serialize an array.
- Keep scalar leaf elements text-only unless nested JSON objects are required.
- Do not map from conceptual JSON paths directly to Oracle source fields. Always express the mapping as generic XML source XPath to provider-shaped XML target path.
- For JPM-style AVS, use seeded/current JPM request and response templates as the strongest pattern evidence when available. Treat SurePay or other provider experiments as useful examples only after confirming the artifacts are accepted for the current implementation.

## Generic Normalized Response Shape

Response templates normalize provider responses into:

```xml
<BankAccountVerificationResponse>
  <RequestId>...</RequestId>
  <BankAcctVerifRespCode>...</BankAcctVerifRespCode>
  <BankAcctVerifRespMsg>...</BankAcctVerifRespMsg>
  <BankAcctVerifStatus>SUCCESS|NEUTRAL|FAILURE</BankAcctVerifStatus>
  <BankAcctVerifIntMsg>...</BankAcctVerifIntMsg>
  <OwnerVerifRespCode>...</OwnerVerifRespCode>
  <OwnerVerifRespMsg>...</OwnerVerifRespMsg>
  <OwnerVerifStatus>SUCCESS|NEUTRAL|FAILURE</OwnerVerifStatus>
  <OwnerVerifIntMsg>...</OwnerVerifIntMsg>
</BankAccountVerificationResponse>
```

For JSON responses, first identify the XML shape produced by Oracle's JSON-to-XML conversion. Build response XSLT using that XML shape. Keep a separate note that relates provider JSON properties to converted XML elements when the conversion is not obvious.

Known internal-message values from the existing JPM-compatible pattern include:

- `ORA_BANK_ACCT_VALID`
- `ORA_BANK_ACCT_INVALID`
- `ORA_OWNER_VALID`
- `ORA_INFO_NOT_FOUND`
- `ORA_SOFT_MATCH`
- `ORA_PROVIDER_ERROR`
- `ORA_TIMEOUT_ERROR`
- `ORA_CONFIG_ERROR`
- `ORA_GENERIC_ERROR`

## Normalization Heuristics

Use provider semantics, not only enum names:

- Exact account validity and active/payment-pass signals should map to `SUCCESS/ORA_BANK_ACCT_VALID`.
- Invalid account-number signals should map to `FAILURE/ORA_BANK_ACCT_INVALID`.
- Not-found, unknown, unsupported-for-checking, or inconclusive signals usually map to `NEUTRAL/ORA_INFO_NOT_FOUND` unless the provider explicitly says the account is invalid.
- Request-shape, unsupported enum, invalid header, invalid credential/configuration, or malformed JSON errors should map to `ORA_CONFIG_ERROR`.
- Provider outage and timeout errors should map to `ORA_PROVIDER_ERROR` or `ORA_TIMEOUT_ERROR` when distinguishable.
- Exact owner/name matches should map to `SUCCESS/ORA_OWNER_VALID`.
- Close/partial owner matches should usually map to `SUCCESS/ORA_SOFT_MATCH` if the existing business flow accepts soft matches.
- No-match owner results should map to `FAILURE`; if the only available vocabulary is JPM-compatible, use `ORA_BANK_ACCT_INVALID` only for compatibility and document that it represents owner mismatch too.

For organisation APIs with company identifiers, keep name-match and company-id-match semantics separate. A company-id `MATCH` can validate ownership when name matching is absent or inconclusive, but should not silently override a definitive name `NO_MATCH` without documenting the product decision.

## Provider response literals and conflicting evidence

- Copy decisive provider codes/reason values exactly from the cited specification, including spaces and case. Distinguish a machine literal from an explanatory label; record uncertain serialization explicitly. Do not silently compact text or introduce aliases without evidence. Build at least one regression input independently from the source table, not by copying the generated XSLT condition.
- Establish precedence between transport status, provider error entries and positive verification evidence. When the provider contract treats an error entry as a failed operation, a contradictory successful result with a nonempty error entry must not establish account or owner success. Use an inconclusive diagnostic in the established Oracle vocabulary (for example NEUTRAL/ORA_GENERIC_ERROR), or a documented guarded rejection, and retain raw evidence. Do not mistake documented advisory warnings or allowed mixed/partial results for this contradiction.
- Determine a nonempty error from the provider's actual error structure. Absent arrays, empty arrays and whitespace-only entries do not by themselves establish a conflict. Preserve ordinary provider-error and timeout behavior. This rule affects the contradictory response path, not the ability to generate an implementation candidate.
- Regress exact reason values at each documented location; normal success with absent/empty errors; a success/error contradiction; normal error responses; and existing match/partial/no-data behavior. Label deliberately contradictory inputs as robustness tests, not observed provider failures. Keep provider-specific examples and regression payloads in tests/noship, not this reusable reference.

or ordering onto the other. Exact `ORA_` internal-message literals above come from
the response seed. The seed's explicit provider-error branch uses FAILURE; a new
provider's status mapping still requires documented semantics and must not infer
account invalidity merely from a provider outage.

For source-shape tests, check nested field names and applicable ordering, not just
the root or RequestId. A handoff-schema PASS establishes persistence consistency,
not source correctness or output quality. Compare generated transformations with
independently stated provider requirements and expected outcomes. Keep source,
offline generation, attachment, runtime and provider acceptance results separate.
