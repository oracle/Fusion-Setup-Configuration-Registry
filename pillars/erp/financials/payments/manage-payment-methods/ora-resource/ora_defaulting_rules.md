# Manage Payment Methods defaulting rules

Entity/EO defaults are evidence of implementation behavior, not automatic package values. Do not serialize a default into an FSM candidate until its field-level application and omission behavior are confirmed. Source IDs are in the Attributes Workbook.

## Reviewed UI design defaults

These proposed design selections were corroborated by a reviewed UI example and same-task export. They are not proof that an omitted field receives the same value in an FSM import or that every payment method should use this profile. Detailed observation records are retained in the authoring evidence.

For a new method with no stated preference for these optional child settings, preselect the following **UI design defaults** in the proposed configuration. Show the choices to the implementor and preserve every explicit override. These defaults guide the conversation and task plan; they do not authorize automatic FSM CSV serialization or imply that omitted CSV fields receive the same values. Do not insert the example's method name/code, creator, login, audit timestamps, or environment values into a reusable skill or package.

The screenshot selections explain this example's child rows but do not define a portable reconciliation key. The `All` UI selection and blank exported scope columns must remain distinct concepts until the service's CSV mapping is proven. In particular, do not fill blank applicability key components merely to satisfy the adapter.

- Parent identity: take `PaymentMethodCode` and `PaymentMethodName` from the implementor; use the requested effective date rather than a fixed date. The export's `EndDate` was `4712/12/31`; treat it as a product sentinel observed in this profile, not a required user input.
- Parent flags: `PaymentFormatAplFlag`, `BankChargeBearerAplFlag`, `PaymentReasonAplFlag`, `PaymentReasonComntAplFlag`, `RemittanceMessage1AplFlag`, `RemittanceMessage2AplFlag`, `RemittanceMessage3AplFlag`, `UniqueRemittanceIdAplFlag`, `UriCheckDigitAplFlag`, `DeliveryChannelAplFlag`, `SettlementPriorityAplFlag`, `ExclusivePmtAplFlag`, and `ExternalBankAcctAplFlag` exported as `O`. `SupportBillsPayableFlag` and `SeededFlag` exported as `N`; `PmtEnableAp`, `PmtEnableAr`, and `PmtEnableCe` exported as `Y`. `SeededFlag` is product-owned and must not become implementor input.
- Parent optional values: anticipated float, payment mode, document category, maturity offset, description, and flexfields were blank in the exported example. A blank is an observed absence, not an instruction to erase an existing value on update.
- Applicability: the reviewed UI-generated rows used `PaymentFlow=DISBURSEMENTS`, the example method code, blank `ApplicableValueFrom`, blank `ExcludeFromApplicFlag`, and blank BU/LE names. `CROSS_BORDER_FLAG` and `FOREIGN_CURRENCY_FLAG` each had AP and AR rows with `ApplicableValueTo=FOREIGN_AND_DOMESTIC`. `PAYEE` had AP, AR, and CE rows; `PAYER_LE` and `PAYER_ORG` each had AP and AR rows; `PAY_PROC_TRXN_TYPE` had AP, AR, and CE rows. Those ten rows had blank `ApplicableValueTo`. Do not infer a portable child key or an import-ready row set from this UI export.
- Translation: the example exported `US` and `KO` rows, both with `SourceLang=US` and the same payment-method name. Language coverage is environment and locale dependent; confirm intended translations rather than generating `KO` for every method.
- Validation assignment/value: the example contributed no rows. Do not create validation children without an explicit design and their configured validation context.

Nullable and type-specific identity requires uniqueness and ignores scope value only for the two reviewed flag types. UI observations alone do not prove portable identity or FSM omission/acceptance behavior. Retain package-specific missing/ambiguous-parent rejection and the standard-default qualification boundaries below.
