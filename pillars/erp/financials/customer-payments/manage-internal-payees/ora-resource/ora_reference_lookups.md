## Criterion selection boundaries

Country-set operators apply only to COUNTRY_PR and COUNTRY_PY with IN/NOT_IN. Other reviewed country facets store TerritoryCode. No implicit active/obsolete country filter or accepted-card filter is added. For YES_NO use the selected lookup context; a public endpoint does not broaden allowed parameter/operator combinations. ORG_ID identity lookup does not establish MOAC visibility equivalence.

Card-brand SOAP is explicitly deprecated and unsupported. Subscription parties are not the general HZ_PARTIES domain. Use the supported FSM card export contract above. Application resolution and PERSON/ORGANIZATION resolution use the qualified routes above. Existing unchanged same-environment values are preserved. Receipt-method identity GET must be accompanied by the stated eligibility evidence; never infer eligibility from a name match.

## Dependency evidence qualification

Card-brand FSM export supplies canonical codes, translations and both acceptance states. Bind task, environment, completed process, release, acquisition time and artifact digest before resolution; reacquire if freshness is uncertain. This reference dependency does not require a card-brand authoring skill or mutation. Do not call the deprecated SOAP service.

Shared CX Organization/Person profiles and target GETs corroborate PartyId/PartyNumber identity. Preserve numeric PartyId in Value; use PartyNumber only where the API contract requires it. Other party types are outside qualified automatic coverage and require identity evidence only if requested; do not reject unrelated or unchanged selections.

Use the taxonomy applicationLOV BOSS GET for source-product selection. Require the APPLICATION stripe and map alternativeId, not moduleGUID. The earlier genericLookups projection is superseded as the primary application resolver.

## Read-only account membership before import

Use `erp.financials.payments.manage-payment-systems` and `shared.setup-export.task-level-export` for task `IBY_MANAGE_PAYMENT_SYSTEMS`, owning context Financials / Payments (`ORA_FIN_PAYMENTS`). Request a fresh populated whole-task export with no criteria. Retain its actual process identity, successful terminal result/log, package hash, environment, principal, acquisition time and release. A partial, failed, unavailable or stale package cannot establish absence. This is evidence acquisition only; it creates no payment system, account, Run Book or setup import.

Read `IBY_PAYMENT_SYSTEM.csv` and require one exact root `Suffix`. Read `ORA_IBY_PAYMENT_SYSTEM_KEY.csv` and match both `IBY_PAYMENT_SYSTEM.Suffix` and `Key1`, with exact raw equality and complete CSV/header validation. Require one exact account row. Zero matches in that complete successful export establish the requested tuple is missing; multiple matches are ambiguous and stop selection. Do not choose the first row, normalize names, substitute another account, or use an import to discover existence. Account-option definition/value CSVs are not account membership lists. Inspect only required identity fields and existing Ownertype; do not print credentials, account-option values or unrelated attributes.

This route does not expose or establish `BepAccountId` or `Ownerid`. Leave import-resolved IDs to the normal import. Exported Ownertype and a general account row do not prove which payee owns the account. Retain the separate payee-bound UI check below and disclose any approved first-use ownership effect.

## Account evidence through the supported UI

The general Manage Payment Systems account table can establish that the exact named account exists under the selected payment system. It does not, by itself, establish its owning payee. For ownership verification after first use, select the exact Internal Payee and inspect its payment-system account table: the account table is scoped to the selected payee. Record the selected payee, payment system, account key, target environment, principal, acquisition time and the observed table context. An account name found only in the general system table is insufficient ownership proof. Close inspection without saving changes.

If an execution surface cannot access that UI, disclose the missing UI capability and obtain current target-bound read-only evidence from the authorized operator. Preserve that handoff as assisted evidence. Do not invent a REST route, infer owner identity from its omission in an export, or mark ownership verified from import acceptance alone.

The same-target AR export supplies class/method/account-assignment hierarchy. receiptMethods and cashBankAccounts GETs confirm identity and AR-use field availability. Check the exact exported method/account assignment and business unit, then verify the account is internal, not a netting account, visible to the authorized principal, AR-enabled and associated with a branch. A one-row probe never establishes exhaustive membership.

## Receipt eligibility composition

Bind the complete AR export and GET evidence to the same current target and authorized principal. Require the exact receipt class/method hierarchy and at least one uniquely matched exported bank-account assignment with the same business unit. Verify an internal, nonnetting, principal-visible account, a bank branch and bank-account ArUseAllowedFlag=true. Class must be MANUAL or AUTOMATIC, with RemitFlag=Y and ConfirmFlag=N. Do not add account-use AR flags, primary, date or currency restrictions unless required by the selected task contract. Incomplete pagination, missing context or ambiguity stops the affected selection. Identity lookup success alone does not establish eligibility or persisted import success.
