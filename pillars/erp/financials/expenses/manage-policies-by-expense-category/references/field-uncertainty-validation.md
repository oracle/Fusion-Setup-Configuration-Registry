# Exact-field application validation


Airfare, Car Rental, Mileage, Miscellaneous and Per Diem sources identify their
owning services/EOs, existing-row alternate keys, mappings and deterministic
rules. Broader target field-write behavior remains evidence_unresolved for
their eligible existing-record business updates. This application-validation
option covers only the exact non-key updates admitted by each owning contract;
it is not a supported-field claim or a way to admit an unsupported operation.
Bounded new-record profiles instead use their separately source-qualified
managed, derived, association and explicit-empty recipes described in
[Supported profiles](../SKILL.md#supported-profiles). The selected five-category
create case passed [live reconciliation](live-verification-scope.md); that result
does not resolve broader existing-update field uncertainty or establish other
target/build parity. Existing-parent/new-child and other unadmitted
branches retain their own blockers. Airfare keeps its full catch-all key and
inherits no Car Rental currency rule or Meals import observation.

Candidate preparation runs workbook, package, target provenance/freshness,
identity, parent association, source ownership, resulting-state, currency and
lookup checks before offering this option. It then computes the proposed ZIP
in memory. Without an exact implementor decision, it emits no candidate ZIP.
The ordinary build CLI writes `field-uncertainty-plan.json` in its new project
output directory and reports `implementor_decision_required`.

The plan includes each entity, complete target key, exact field, before/after
value, unresolved question, expected failure surface and Source IDs. It binds
the workbook, baseline, runtime contract, target environment/origin, validation
date and would-be candidate SHA256. Show that entire plan to the implementor
before recording acceptance. Do not infer acceptance from Step 7, a general
continue instruction, export approval, another field, or another candidate.

After explicit acceptance, record a local JSON decision with exactly:
`schema_version` = `1.0`, `plan` = the entire unchanged displayed plan,
`implementor_approval` = `accept-evidence-uncertainty`, and `acknowledgement` =
the implementor's informed acknowledgement. Do not create this decision on the
implementor's behalf before they respond. Pass its absolute regular-file path
as `--field-acceptances`, or the public protocol's
`resolvedScope.policyPreparation.field_acceptances`. Changed plan/input/target,
unused decisions, symlink files and duplicate JSON keys are rejected.

The public protocol retains the corresponding
`evidenceUnresolvedUpdateOverrides` and warnings. Ordinary native rule evaluation
also reports the exact uncertainty and failure surface. The decision hash is
part of the immutable input binding. Fields remain evidence_unresolved after
acceptance; no live qualification is inferred.

Keys, parent references, IDs, audit values, status, dates and currencies cannot
use this option. Source-proven invalid or out-of-scope fields, unsupported
operations, missing lookup evidence, malformed packages, ambiguous identity and
missing target authority remain blocking. All omitted values and unrequested
rows must be preserved. Native Task Hook/Run Book/Data Loader immutable preview
and candidate-specific approval remain required. Submit once, retain diagnostics
and reconcile a fresh export. Failure requires a new business decision and
preview; it never authorizes retry.
